## [0.9.0] - 2026-10-07

The first internal release.

### Added
- Build Forge settings are stored inside their Unity Build Profile, as a Build Profile component in the profile's `.asset` (Unity 6.3+ component API), so they share its name and file, and renaming, duplicating or deleting the Build Profile carries them. They are edited in a "Build Forge" section of the Build Profile editor (the Build Profiles window, and the Inspector for a Build Profile asset), which also adds and removes them, and from Assets > Build Forge (several Build Profiles at once) or the Build Profile inspector's context menu; the Assets > Create menu no longer makes separate profile assets
- Per-profile **Remove Previous Build Output** option, on by default for new and existing profiles, with an Inspector warning when off; applies to editor and CI builds. Before each build it removes the artifact file and the files the previous build of that profile and variant produced (recorded per user in `UserSettings`); files that were already in the destination, or changed since, are kept. No old APK, AAB or Windows/Linux executable survives a later failure (a macOS .app bundle and directory outputs are cleaned only from the build record); unsafe output directories are rejected, and the build stops when the destination cannot be read or a file cannot be deleted
- Generated CI commands use `unity run` for project-version lookup, with reserved launcher flags omitted and Accelerator upload waiting enabled. Subfolder project paths start with `./`, so Unity CLI does not read them as registered project names. Direct Editor entry points remain supported.
- `BuildForge.CommandLine.Activate` with `-forgeBuildProfile "<path>"` activates a profile in a batch run of its own, like the build window's Activate, and exits with 0 or 1. Run it before a build that changes platform: across a platform change, Unity 6000.3.23's `-activeBuildProfile` compiles the new profile's defines for the previous platform first, so code that needs a platform-only assembly fails to compile before Build Forge runs (6000.3.0 and 6000.6.4 switch first). The build rejects `-forgeBuildProfile` and points to Activate. The build window's CI Command shows both commands, **One workspace per job** and **Shared workspace** (Activate, then the build); the sample scripts take `-SharedWorkspace` and `--shared-workspace`, and the sample Jenkins pipeline and GitHub workflow, which build any profile in one workspace, activate before every build
- Native player-build failures restore the full preloaded-assets list before Forge plugin cleanup, including when Unity skips XR postprocessors.
- Restored settings are written to the native Build Profile's embedded PlayerSettings as well as the live settings, including CLI version overrides and Android signing.
- Reject invalid/duplicate variant rules, invalid/generated scripting aliases and stale profile restrictions before editor Apply or CI overrides; surface configuration errors in both inspectors.
- Validate native development-setting compatibility before editor plugin changes; preserve reserved-name diagnostics.
- Document XR loader selection as optional for all projects, the OpenXR-before-content execution order, and Windows-only CLI/player proof coverage. The proof runner pins the actual selected Editor version.
- Variant rules have a Version: a template for Player Settings > Version during the variant's builds, with `{Version}`, `{BuildNumber}` and `{Variant}`, for example `{Version}.{BuildNumber}d`. It is filled in after the plugins' pre-build steps and restored right after the player build; a build without a build number keeps the version, with a warning in the build window and the log. The manifest's `BuildNumber` now carries the Build Number plugin's number on every platform, not only Android's version code and iOS's build number
- Variant rules have a Build Configuration: Unity build settings for the variant's builds, each Inherit by default. The development options (Autoconnect Profiler, Deep Profiling Support, Script Debugging, Wait For Managed Debugger); C++ Compiler Configuration, IL2CPP Code Generation and IL2CPP Stacktrace Information; Managed Stripping Level and Strip Engine Code; Compression Method, and on Android Link Time Optimization and the Debug Symbols level. They are set for the build and restored afterwards, the per-platform Player Settings exactly as Unity stored them, so `ProjectSettings.asset` and the Build Profile are unchanged; Apply never writes them. A rule that turns a development option on while turning Development Build off, or Wait For Managed Debugger on while turning Script Debugging off, is an error, and the build window and the build log warn when a development option would go unused. The build window shows the settings on a Build Configuration line
- OpenXR profiles can use **Only Listed Features**, an allow-list like the per-headset feature lists of per-platform switching code: builds and Apply turn the ticked features on and every other visible feature off, so a feature a package update adds stays off until it is ticked. Hidden features, which vendor SDKs register for their own use, are left to their packages and listed read-only. Switching the mode keeps what builds get. The build window's OpenXR line and the build log name the features turned off because they aren't listed, and the manifest records `onlyListedFeatures`. In either mode the plugin warns about an override on a hidden feature. Plugin descriptions in the build window wrap instead of being cut off
- Play Mode follows the applied profile's XR: Play Mode runs on Standalone's XR settings, so applying a profile of another platform also copies that platform's XR loaders (without loaders whose provider doesn't support Standalone), Initialize XR on Startup and OpenXR feature on/off states to Standalone. Revert to Baseline, drift and builds treat it like the plugins' settings. **Project Settings > Build Forge > Play Mode Follows Applied Profile**, on by default
- OpenXR validation for ignored interaction-profile overrides and unavailable enabled features; manifests now include the effective enabled feature list alongside configured overrides. The warning that OpenXR is not a plug-in provider for the profile's platform appears only when the profile has OpenXR overrides, which would have no effect.
- OpenXR warns, in the build window, the profile inspector and the build log, about a settings override on a property that a feature enabled in that profile's build also declares (such as symmetric projection, which Unity's Meta Quest build step copies from MetaQuestFeature), since it may not reach the player. A disabled feature's build steps don't run, so a profile that disables the feature can override the setting, and the inspector shows it there. The manifest lists the feature pins of the features a profile enables, one `FeatureType.path` entry each. With OpenXR 1.18, Android profiles also warn (window, inspector, build log) when OpenXR will turn the Meta controller profiles and Meta Quest Support off at the next editor load, because it enabled them for a Meta Quest Build Profile that is no longer active.
- With OpenXR 1.18, a build of a Meta Quest Build Profile enables the Oculus Touch, Meta Quest Touch Pro and Touch Plus interaction profiles and Meta Quest Support for Android while `ProjectSettings/BuildProfileUtilityOpenXR.asset` says OpenXR has not, as OpenXR does when the editor loads with such a profile active, a step batch builds skip; the settings are restored after the build. A CI build of a Meta Quest profile no longer depends on whether the committed OpenXR settings still hold them. The README documents Meta Quest Build Profiles.
- Optional variant rules for Unity development flags, additional defines and product marking; per-profile restrictions with explanations.
- Variant-aware validation, build descriptions and editor Apply hooks, with saved editor-variant restoration after builds and failures.
- Ordered XR Management loader selection, explicit empty selection, persisted editor snapshots and build restoration; OpenXR validates the intended selection.
- Additional Addressables group and label exclusions per variant. Exclusions left under a renamed or removed variant stop the profile's builds until they are moved to a variant or removed in the inspector, instead of silently not applying.
- Unity 6000.3.23f1 player proof and failure-injection workflow; optional XR/Addressables tests.
- Build window laid out like Unity's Build Profiles window, with the Build Forge anvil in its tab (in light and dark theme versions): a list pane on the left (platform icon and name, click to select, double-click to open the inspector, Active/Applied status), a details pane on the right for the selected profile (Unity Build Profile, platform, output path, scripting define, issues, the plugins that run for this build in order with what each will do and skip reasons, CI command), and a pinned action bar (Activate \<profile\> / Apply \<profile\> / Build / Revert to Baseline)
- Build Profile and apply dropdowns in Unity's main toolbar (Unity 6.3's main toolbar API), one element named Build Forge that the user places like any toolbar element: picking a profile activates it like the build window's Activate; the apply dropdown shows what is applied like the window's Editor line ("Applied (Internal)", drift), applies the active profile like Apply, with the variant you pick when the project has variants, and offers Revert to Baseline whenever something is applied. Shown by default, although Unity starts package toolbar elements hidden; hidden with Unity's toolbar menu (right-click > Hide, or ⋮), and the choice is kept per user in `UserSettings/ForgeUserPreferences.asset`, so it survives a layout reset
- Activate \<profile\> (Unity's Switch Profile, after reverting another profile's applied plugin settings; the profile that is still applied keeps them) and Apply \<profile\> (for the active profile, writes participating plugins' overrides to the global settings); a per-plugin baseline stored per user in `UserSettings/ForgeEditorState.asset` (persisted before each plugin writes) guarantees switching profiles never stacks, builds always run from the baseline plus the built profile's deltas, and drift from the applied state is flagged with Re-apply / Revert to Baseline / Dismiss Drift actions in the build window. The applied state is keyed on the Unity Build Profile; when Unity is switched to another Build Profile or to a platform profile (Unity's Platforms list, `-buildTarget`, a deleted `Library/`) without Build Forge, the window warns that the previous profile's plugin settings are still applied, and activating that profile again keeps them
- A failed restore keeps its baseline for retry, persists partial recovery and stops Apply and Activate. A failed Revert to Baseline lists what it could not restore and offers Stop Tracking, so a setting that can never be restored (its plugin's package removed, a deleted XR loader) does not block Apply, Activate, Revert and builds for good. Builds stop when the applied state cannot be suspended, and CI fails when it cannot be resumed, keeping baselines and the previous expected snapshots for failed entries
- `IForgeEditorApplicable` — optional plugin capability for editor application (implemented by the OpenXR and XR Loaders plugins)
- One set of Build Forge settings per Unity Build Profile: more than one is an error in the Build Forge section and the build window (the profile cannot be selected, applied or built). The Unity Build Profile's name is the name used everywhere (build window, `{ProfileName}` output-path placeholder, manifest, scripting define)
- Build variants (Project Settings > Build Forge > Build Variants): project-wide names that add one `BUILD_VARIANT_<NAME>` define to a build of any profile, with optional rules for development mode, extra defines, product marking and variant-aware plugin behavior. Chosen per build in the build window or with `-forgeVariant` in CI; once any variant exists the default build gets `BUILD_VARIANT_DEFAULT` and "default" is reserved; the define is put on the Build Profile for the duration of the build and restored afterwards, or, with the rule's aliases, written while the variant is applied to the editor (a rule's development flags only ever apply to builds, so a Build Profile committed while a variant is applied cannot make other machines' Default builds development builds); a `BUILD_VARIANT_` define on a Build Profile that is not applied on this machine, saved while a variant was applied elsewhere, is reported in the build window, the inspector and the build log, and Activate removes it with the rules' aliases; `{Variant}` output-path placeholder (`Default` for the default build once variants exist, so default and variant builds are siblings); recorded in the manifest as `BuildVariant`; variant builds are marked in the product name ("Game (Internal)", so file name and app name show it; never the default build; off switch Mark Variant Builds)
- Scripting define per Build Profile: Build Forge keeps `BUILD_PROFILE_<NAME>` in each referenced Unity Build Profile's Scripting Defines list (replaced after a rename, user defines untouched), so code can compile conditionally per profile; a warning flags two profile names that sanitize to the same define. Off switch in Project Settings > Build Forge > Profiles > Maintain Build Profile Defines. On early Unity 6000.3 patches, where Unity's own Build Profiles window would then ask to apply or revert the active profile's changed defines (and Revert would undo Build Forge's change), Build Forge's define writes, including a variant's, also update Unity's record of the compiled defines, so it does not ask
- Build Forge settings are saved to disk right after an Inspector edit, so the Build Profile's `.asset` file always matches the Inspector instead of lagging until Save Project or quit. Opt out in Project Settings > Build Forge > Profiles > Save Profiles On Edit
- Plugin system with zero-config discovery via `[ForgePlugin]` attribute and `TypeCache`
- Plugin validation API for pre-build warnings (e.g. missing XR provider, Player Settings overrides shadowing)
- `IForgePlugin.DescribeBuild(profile, isCI)` — optional one-line description of what a plugin will do in a build, shown in the build window
- Plugin execution order: each bundled plugin has its own multiple of 100 (100–800), so their order is fixed; external plugins pick values in between, or 1–99 to run before all of them
- Plugin configuration stored as native serialized objects (`[SerializeReference]`), per profile via `ForgeProfile.GetPluginConfig<T>` / `SetPluginConfig` and globally via `ForgeSettings.GetGlobalPluginConfig<T>` / `SetGlobalPluginConfig`, so profile and settings assets are readable and line-diffable. Fields with a fallback default (Build Number env var name, global Android Keystore Env var names) store empty until a name is typed, so a value in the YAML always means it was chosen
- Player Settings diff view with YAML-to-YAML comparison and rich rendering (color swatches, object thumbnails, enum names, boolean Yes/No); per-platform dictionaries and lists, batching included, are compared for the selected profile's target (the Server entries for a Dedicated Server profile)
- Inline Player Overrides foldout in the Build Forge section, with diff count
- Standalone Player Overrides window for inspecting any Unity Build Profile
- Player Overrides window Matrix mode: every Unity Build Profile with Player Settings of its own side by side, one row per Player Setting that differs from Project Settings in any of them, each platform's profiles led by that platform's Project Settings values, with matching values dimmed, values every profile holds unlike Project Settings marked as possibly stale, click-to-select and markdown copy. Opens by default; Single Profile is the previous view
- Build manifest added to the player's StreamingAssets at build time from a `Library/` folder via `BuildPlayerContext.AddAdditionalPathToStreamingAssets`, so the project's Assets folder is never touched (`BuildProfileName` is the Unity Build Profile the build was made from; `DevelopmentBuild` and, on Unity 6.6+, `ManagedCodeVariant` record how the player was built), readable at runtime via `BuildManifestLoader.Load()` and `BuildManifestLoader.LoadAsync()` (concurrent `LoadAsync` callers share one in-flight load; on WebGL use `LoadAsync`, `Load()` warns and returns null there). The build fails when an enabled manifest cannot be written or is missing when the pipeline injects it
- The package declares the built-in modules it needs, JSON Serialize and UnityWebRequest (the manifest loader on Android and WebGL), so the Package Manager enables them in a project that disabled them. Before, such a project failed to compile Build Forge, or its Android and WebGL players
- Build interception to enforce pipeline usage
- Build summary logging (time, size, status)
- Successful editor builds are shown in the file browser afterwards (Explorer / Finder / Linux file manager), like Unity's own Build button; never in CI. Off switch in Project Settings > Build Forge > Output > Reveal Build In File Browser
- CI command line support: the build uses the Build Forge settings of the active Unity Build Profile (`-activeBuildProfile`); a Build Profile without them, or with more than one set, fails the build with exit code 1. `-forgeVersion` and `-forgeVersionCode` override `bundleVersion` and Android `bundleVersionCode` for one build. Build Forge's arguments all start with `-forge` and match case-insensitively; an unknown `-forge` argument or a Build Forge argument without a value (missing, followed by another flag, or empty) fails with exit code 1, so a typo or an unset CI variable cannot silently build the default variant or the project's own version
- `ForgeBuildContext.IsCI` — batch mode by default, overridable with `-forgeCI [true|false]` or the `FORGE_CI` environment variable (an unrecognized value of either fails a CLI build) — so plugins can skip build-machine-only work on developer machines
- Output path sanitization for `{ProjectName}` placeholder (spaces, special characters replaced for safe filenames)
- Auto-append platform file extensions (.apk/.aab/.exe/.app)
- Git Metadata plugin (branch, commit hash, short commit hash, git describe, exact tag in manifest)
- Build Number plugin (build numbers from the git commit count, a configurable environment variable, or that variable on CI and the commit count locally, with offset; the last uses the same CI detection as Cloud Diagnostics, and the inspector shows both outcomes). The build fails before PlayerSettings change when the environment variable is missing or not a whole number of 0 or more, which the build window lists as an issue beforehand, or when base plus offset is outside the non-negative 32-bit range, which the preview shows
- Android Keystore Env plugin (override the keystore path and password, key alias and key password from environment variables for CI builds, by default `ANDROID_KEYSTORE_PATH`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS` and `ANDROID_KEY_PASSWORD`, with global defaults, per-profile Inherit/Override, per-profile opt-in, and fail-fast validation of empty secrets and debug-signed misconfigurations). A build that overrides nothing leaves Player Settings untouched, and the keystore path is restored exactly as stored, so an empty one no longer comes back as `{inproject}: `
- Cloud Diagnostics plugin (per-profile crash reporting mode: Always / CI only / Never; controls Unity's automatic symbol upload; off by default)
- OpenXR plugin (per-profile feature toggles, per-feature settings pinned property by property through the native feature editors, top-level settings overrides, full-snapshot restore after builds that also undoes settings written by Unity's Meta Quest build hook)
- OpenXR validation warnings (build window and profile inspector): ticked feature groups force-enable their required features, and a build stops on a per-profile Disable override that one of them blocks, with an error naming the group; while a Meta Quest platform profile is active, Disable overrides on the three Meta interaction profiles are undone by Unity on every domain reload
- Addressables Rebuild plugin (rebuild content before building, off by default)
- Addressables Stripper plugin (per-profile group/label exclusion; excluded labels move their entries into a temporary non-built group for the duration of the build, so they are neither packed nor loadable)
- Project Settings integration with plugin enable/disable, global plugin settings, and one-click package install for optional plugins
- Sample: runtime manifest reader using async loading
- XR Vendor Filter plugin (Android): keeps the SDKs of the packages a profile excludes out of its builds. Their Android libraries never reach the Gradle project (Unity's include-in-build delegate, set after the vendors' own pre-build steps); the manifest entries Meta's and Pico's Gradle steps write into every Android build are removed after those steps (`com.oculus.*`, `com.meta.*` and Horizon OS for Meta, `com.pico.*` and `com.picovr.*` for Pico, plus extra prefixes); a leftover check fails the build if an excluded library or entry remains, including in the manifests of the remaining libraries. The inspector lists the installed XR vendor SDKs that ship Android libraries by vendor (Meta, Pico, Steam), and folds the other packages that ship them, Unity's XR packages among them
- Android Manifest plugin: a profile's own main manifest, swapped in for its builds with Custom Main Manifest on, and the project's file and setting restored afterwards
- `IForgeGradleProcessor`: an optional plugin capability for a step in an Android build's generated Gradle project, called after the vendors' own Gradle steps in plugin order
- User manual in `Documentation~/`: installation, concepts, plugins, CI, plugin authoring, integration guide, troubleshooting
- Sample: Example Integration, an Application ID Suffix plugin for variant builds and CI scripts (Jenkins, GitHub Actions, PowerShell, bash)
