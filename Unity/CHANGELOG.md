# Changelog

All notable changes to Build Forge will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed
- The Example Integration sample's `Build-Player.ps1` and `build-player.sh` hand `unity run` a relative project path as `./<path>`. The Unity CLI takes a bare name as the name of a project registered in Unity Hub first, so `-ProjectPath Client` (`--project Client`) built the registered project of that name, if there was one, instead of the `Client` folder
- The OpenXR, Addressables Stripper, Addressables Rebuild and XR Loaders plugins compile only with OpenXR 1.16.0, Addressables 2.7.4 and XR Plug-in Management 4.5.3 or later: the versions Unity 6000.3.0, the oldest editor Build Forge supports, installs, and the oldest they were tested with. They used to compile with OpenXR and Addressables from 1.0.0 and XR Plug-in Management from 4.0.0. The OpenXR plugin also needs XR Plug-in Management 4.5.3, which its XR Loaders code uses, so a project that pins an older one leaves out both plugins instead of failing to compile. With an older package the plugin is left out, and builds and Apply of a profile that stores its settings stop until the package is updated, as do those of every profile while Project Settings > Build Forge stores OpenXR settings; where such a profile is applied, Revert to Baseline before updating Build Forge, or update the package first, since Build Forge can't restore what the plugin applied without it
- Project Settings > Build Forge > Installed Plugins lists the on/off switches of plugins that aren't installed, because the plugin was renamed or moved or its package was removed or is older than the plugin needs, each with whether it was on or off and a **Remove** button. Such a switch changes no build, so a renamed plugin starts from its default, and a reinstalled or updated package uses its switch again; it used to stay in ProjectSettings/ForgeSettings.asset without a word
- A plugin that throws while the build window, the Build Forge section or Project Settings ask it for its name, description, applicability, switch, build description or warnings no longer breaks the window: it shows a fallback and logs the error once. The build window used to lose its action bar and repeat the error on every repaint. A plugin's own drawing code is not caught
- The build window says **Settings changed: Refresh to update the warnings.**, with a **Refresh** button, in the selected profile's details when a profile's Build Forge settings, its Build Profile's scripting defines or Project Settings > Build Forge change after it computed its warnings, which it does when it opens, on Refresh, when a variant is picked and after its Activate, Apply and Revert to Baseline. It used to go on showing the old warnings without a word
- A plugin that is on in Project Settings and throws when asked whether it runs for a profile, in `IsApplicable` or `IsEnabled`, stops builds and Apply of that profile before they change anything, with the error in red in the build window, which disables Apply and Build, as the main toolbar does. Builds used to stop on the raw exception after removing the previous build output, and the build window stopped drawing
- A build logs a plugin that is switched on for the profile but doesn't apply to its Build Profile, with the reason, instead of skipping it without a word
- A plugin whose `Order` throws is listed as failed to load, so builds and Apply stop while it is on in Project Settings. It used to leave the plugin list unsorted, and builds ran the plugins in the order Unity found them without a word
- The Example Integration sample's Application ID Suffix plugin stops a build when it lists a variant that is no longer configured, instead of only warning in the build window: the renamed variant's build got the production application identifier. The plugin guide recommends the same for any plugin that stores variant names
- With Maintain Build Profile Defines on, a CI build stops when its Build Profile lacks its `BUILD_PROFILE_` define or carries a stale one, as after a rename outside the editor, instead of building the player with the wrong `#if` branches after a log warning. A local build still warns, since the build window adds the define
- A command-line build with `-forgeVersion` or `-forgeVersionCode` runs the build's checks before it sets them, and on CI the check of a variant rule's Version uses the `-forgeVersion` value. A run that a check stopped, such as for a disabled platform or a plugin that failed to load, used to set the version, put it back and save the Player Settings and every other unsaved asset
- A build that did not finish stops every later build until it is cleared. A build writes `UserSettings/ForgeBuildInProgress.json` before it changes anything and removes it once everything is put back; a crash, a killed editor, a CI timeout or a failed restore leaves it behind, and the project files may still hold what that build changed, which the next build used to start from and keep without a word. The build window shows it with **Clear**, and the message says to check `git status` and `git diff` and restore the files that build changed. The crash-recovery advice in ARCHITECTURE no longer suggests folder-wide `git checkout`, which also discards your own changes. Apply and Re-apply stop too, and the build window and the main toolbar disable them, since an Apply would record what that build left as the baseline that Revert to Baseline and builds put back; Revert to Baseline and Activate stay available
- While a profile is applied and nothing has drifted, the build window's reminder names what is applied: the setting groups as the drift notice names them, such as `OpenXR (Android)`, and the variant's defines with the Unity Build Profile that holds them, and says to Revert to Baseline before committing them and Apply again afterwards. It used to say only that the applied settings live in version-controlled assets
- The Build Number plugin's preview in a profile's Build Forge section reads an environment variable each time it draws. It used to reuse the last profile's number, or its shallow-clone note, for a few seconds, so a profile with another variable or another source could show the wrong preview; builds were never affected
- The build window's **Shared workspace** CI command has an **Activate** and a **Build** button, which copy one command each, for a CI step each, in place of one **Copy** for both: pasted as one script, the build also ran after a failed Activate. The CI Command section warns when the project or Build Profile path holds a character a shell reads inside the copied double quotes, such as `$`, a backtick, `%` or `!`
- The Player Overrides window says it could not compare a profile's Player Settings when Project Settings can't be read, or when the two have no setting in common because a file wasn't read as expected, instead of calling them identical or matching. The Single Profile view used to say "identical" when ProjectSettings.asset couldn't be read. The manual says the window needs assets serialized as text. In the Matrix such a profile keeps its column, so it can still be selected, but its cells stay empty and its title, tooltips and **Copy** say not compared; it used to show Project Settings values there as the profile's, and kept a value that every other profile shares from being marked possibly stale
- The Player Overrides window treats values that differ only in spacing, such as `My  Game` and `My Game`, as different. It used to collapse every run of spaces and show them as identical; only the line breaks and indentation Unity lays nested values out with are still ignored
- On Windows, Remove Previous Build Output also checks where the destination leads through a junction or symbolic link: a destination that leads into the project's `Assets` or another protected folder, the package source or Git metadata stops the build, as one written there does. A link pointing into `Assets` used to pass, and files saved there during a build could be recorded as build output and removed by the next build. macOS and Linux still check the path as written
- An output path on a network share, such as `\\buildserver\releases\{Variant}`, keeps its leading `\\`: tidying an empty placeholder used to turn it into `\buildserver\...`, a folder at the root of the current drive, without a word. A relative template that starts with an empty placeholder, such as `{Variant}/Builds` in a project without variants, stays relative instead of landing at the drive's root. Extended-length (`\\?\`) and device (`\\.\`) paths stop the build, with slashes or backslashes in any mix, and so does a template that a placeholder's value turns into one, such as a product name that isn't sanitized; the build window and the main toolbar disable Build for a template that is one
- OpenXR: a build or an Apply of a profile whose Disable override, or Only Listed Features, turns off a feature that a feature group ticked for its platform requires stops before OpenXR's settings are written, with an error naming the group, and puts back what it wrote before that. Command-line builds went ahead and shipped the feature off, because OpenXR refuses only for the platform the XR Plug-in Management page showed last, and refuses nothing in batch mode; an Apply only warned and recorded the refused state as applied. With Play Mode Follows Applied Profile's OpenXR Features set to Match the platform's, an Apply also stops when the copy would turn off a feature that a group ticked for Standalone requires. While Build Forge writes a platform's features, OpenXR's own refusal now looks at that platform
- OpenXR: Apply, and Play Mode Follows Applied Profile's copy of OpenXR features, stop when OpenXR refuses a feature's on or off state, and put back what they wrote, as a build already stopped. They used to log a warning and record the refused state as applied, so drift showed nothing while a build of the profile stopped
- With the Addressables package installed but no Addressables settings, a build stops when the Addressables Stripper has exclusions for its variant or Addressables Rebuild is on for the profile, because nothing would be excluded or rebuilt and Unity's player build still copies the content built before into the player. Both plugins used to be skipped without a word. The build window and the plugins' foldouts say so first, and the Stripper's foldout lists the stored exclusions with **Remove**
- A build logs the warnings the build window shows for the profile before it changes any setting: every running plugin's warnings as `[Build Forge/<plugin>] <warning>`, and Build Forge's own, such as an output path without `{Variant}` or a define collision. They used to appear only in the build window, so a CI log never showed, for example, that XR Vendor Filter excluded OpenXR or that OpenXR overrides had no effect. Warnings still don't stop a build, and a plugin's `Validate` that throws is logged as a warning
- Apply stops before it changes anything while a plugin that is on in Project Settings failed to load, or while Unity cannot load plugin settings, as builds already did. Apply used to write what was left and record the profile as applied; a Re-apply first undid the profile's earlier settings, so OpenXR overrides could disappear while the profile still showed as applied. The build window shows the reason in red, and it and the main toolbar disable Apply and Build for the profile with the reason as their tooltip; Build used to stay enabled and fail when clicked
- `ForgeBuildRunner.RunBuild` throws the new `ForgeBuildRestoreException` when the player was built but a restore or cleanup step after the build failed, once every other step has run. It used to return the player's report, which says Succeeded, so a script that judged the build by it took a possibly modified project for a clean build. The exception's `Report` is that report and its `Failures` lists the failed steps. A player build that fails is still reported by the returned report, and the build window, the toolbar and `BuildForge.CommandLine.Build` are unchanged

### Removed
- `IForgePlugin.Validate(ForgeProfile)`, `IForgePlugin.DescribeBuild(ForgeProfile, bool)` and `IForgeEditorApplicable.ApplyToEditor(ForgeProfile, BuildTargetGroup)`, the forms without a variant: Build Forge called only the forms with one, whose defaults called these. Update a plugin by hand: implement `Validate(ForgeProfile, string variant)` and `DescribeBuild(ForgeProfile, bool isCI, string variant)` instead, and, in a plugin that implements `IForgeEditorApplicable`, `ApplyToEditor(ForgeProfile, BuildTargetGroup, string variant)`, which has no default; `variant` is null in a project without variants. An old `ApplyToEditor` stops compiling, but an old `Validate` or `DescribeBuild` without a variant still compiles, as an ordinary method that Build Forge never calls, so its warnings and descriptions disappear without an error
- From the public API, before 1.0 freezes it, members that nothing outside Build Forge needed: `ForgeSettings`' switches `InterceptBuilds`, `WriteBuildManifest`, `LogManifestContents`, `MangleProductName`, `SaveProfilesOnEdit`, `MaintainBuildProfileDefines`, `PlayModeFollowsAppliedProfile`, `RevealBuildInFileBrowser` and `MarkVariantBuilds`, whose setters saved the settings; `ForgeProfile.VariantRestrictionReason` and `ForgeProfile.DefaultOutputPath`; and the setters of `BuildManifest`'s fields and of `ManifestSection.Name`, so game code and plugins read the manifest, and plugins still add sections, named when they are made. An editor script can change the switches as Project Settings does, through a `SerializedObject` on `ForgeSettings.instance` and then `ForgeSettings.instance.SaveSettings()`

## [0.9.5] - 2026-10-21

### Changed
- While an Apply or a build that wrote the applied profile's settings did not finish, builds stop before they start, and so do Apply and Activate of another profile, with a message that names the settings. That happens when the editor quits during an Apply, or during a build while a profile is applied, or when Build Forge couldn't undo a stopped Apply or apply the profile again after a build. **Revert to Baseline** and **Re-apply** of the applied profile restore those settings to their state from before, whole, which also undoes anything changed in them since, and log which settings they restore. The build window explains the state, the toolbar's drift tooltip lists those settings with `(Apply did not finish)` or `(build did not finish)`, and Dismiss Drift leaves them reported. The per-user editor-state file, `UserSettings/ForgeEditorState.asset`, records how far each setting's Apply or build got; files written by earlier versions read as finished, so an Apply or a build interrupted under an earlier version isn't recognized as such: if one was, check those settings in version control after updating
- A plugin's capture right after it applied its settings to the editor (`IForgeEditorApplicable.CaptureEditorState`) that throws or returns null stops the Apply, as a failing capture before it does. The Apply used to succeed and record the settings from before it as the applied ones
- OpenXR: restoring settings, after a build and when undoing an Apply, writes each feature's on/off state as part of the snapshot instead of through `OpenXRFeature.enabled`, so it doesn't run features' on/off callbacks, which can change other features and other platforms' settings, and no feature group can refuse it. A restore checks the snapshot before writing: one it can't read, a feature's settings in it that can't be read, a platform without OpenXR settings, or a value OpenXR can't take now stops the restore, which writes nothing. When undoing an Apply, the settings stay tracked for Revert to Baseline or Stop Tracking, and a build that needed the undo doesn't start. After a build, the build's OpenXR settings stay in place and the build fails; if the applied profile covers that platform, its settings stay unfinished until Revert to Baseline or Re-apply. A platform without OpenXR settings or a value OpenXR can't take used to be skipped without a word, and the build log said "OpenXR settings restored." anyway; a snapshot it couldn't read skipped the restore with only a parse warning. An OpenXR version whose features no longer have the on/off field Build Forge restores stops the Apply or the build before it writes anything. A setting or feature the installed OpenXR no longer has, as after a vendor package was removed, is skipped with a warning

### Fixed
- Since 0.9.3, a plugin that failed part-way through an Apply, or an editor that quit in the middle of one, left that Apply's own writes in place: undoing the Apply treated them as changes made after it and kept them, and the build window then said nothing was applied. The OpenXR settings and the XR Loaders list of a profile could stay in the project's version-controlled settings that way. Build Forge now restores the settings from before such an Apply, whole. The same applies after the editor quit during a build while a profile was applied: undoing it kept the crashed build's settings, and the next build of the applied profile kept them too
- When Build Forge cannot undo the applied profile's settings before a build and applies the undone ones again, it applies them in the order of the Apply, so Play Mode Follows Applied Profile's copy follows its platform's settings again. They were applied in reverse, so the copy took the platform's settings from before the Apply
- After a build, when a plugin couldn't put back its settings, Build Forge no longer applies the applied profile on top of what that left, which then counted as the profile's settings and hid the problem from drift; such settings, and Play Mode Follows Applied Profile's copy of them, stay unfinished until Revert to Baseline or Re-apply. When the applied profile no longer resolves, they stay recorded for Revert to Baseline instead of being forgotten with a message that they were left at baseline
- OpenXR: since 0.9.3, undoing an Apply kept the properties the Apply wrote for a feature that was turned on or off after it, in the project's settings: the feature's settings counted as changed after the Apply because they also hold its on/off state
- The error after failed post-build steps no longer says the build artifact is complete when no player was built

## [0.9.4] - 2026-10-20

### Changed
- `BuildProfileUtility.GetBuildTarget` throws when a Build Profile stores no build target, as a Unity version that renamed the field would, instead of returning the editor's active build target, and `BuildProfileUtility.IsDedicatedServer` throws for a Standalone profile that stores no subtarget instead of answering false
- The Cloud Diagnostics plugin also sets Diagnostics Data (Unity 6.2 and later) for the build, from the same mode as crash reporting, and puts the Unity Build Profile's own value back afterwards. Diagnostics Data, too, makes an Android build upload its IL2CPP symbols and the player report crashes in a project linked to Unity Cloud, so with crash reporting off a build still did both, contrary to what the plugin's manual and tooltip said. A local build with CI Only now has both off. If a Unity version stores no Diagnostics Data in the profile, builds of profiles with the plugin on stop. The manual also says that a build machine, which isn't signed in to a Unity account, needs a token in `USYM_UPLOAD_AUTH_TOKEN`, or Unity's CI route, for the upload
- On CI, a build whose variant rule's Version can't be filled in, such as `{Version}.{BuildNumber}` in a Windows profile without Build Number, stops before it starts instead of building with the plain version and a warning in the log. Local builds keep the plain version and warn, as the build window does beforehand
- Git Metadata's Branch is off by default, so a player's manifest no longer carries the git branch name unless the profile turns it on: the manifest ships in every player, and a branch name can say what a build is for. Profiles that stored Git Metadata settings keep the value they stored

### Fixed
- A build stops before it starts while a Build Forge plugin that is on in Project Settings failed to load, and names the plugin and its error. It used to build without the plugin, with only an error in the console. **Project Settings > Build Forge > Installed Plugins** lists such a plugin, marked "(failed to load)" with its error, so that it can be turned off there
- A build stops before it starts while the profile's Build Forge settings, or Project Settings > Build Forge, hold plugin settings that Unity cannot load because their class is gone or was renamed or moved: after the package that provides the plugin was removed, or after an update renamed the class, as 0.9.1 did by moving six bundled plugins into assemblies of their own. The message names the settings and their class, and the build window shows it before a build. Builds used to go out without such settings and without an error: the plugin read its defaults instead, or did not run at all
- A variant rule's Build Configuration setting that the profile's platform has but Build Forge cannot find, as after Unity renamed its field, stops the build instead of being left out. Development Build and Script Debugging come from the profile and no longer fall back to the editor-wide settings when Build Forge cannot read them
- OpenXR: a build of a Meta Quest profile with Meta Quest Setup on stops when Build Forge cannot read OpenXR's own Meta Quest setup, in OpenXR 1.18 or later, instead of building without the features the setup promises, and the build window says so. For any Android profile, the window warns when that setup can't be checked, or when Build Forge can't tell whether the profile is a Meta Quest profile. Interaction profiles are recognized by OpenXR's own type, so an OpenXR release that renamed it would fail to compile instead of letting Only Listed Features turn unlisted controller profiles off
- A build of a Meta Quest profile, or another derived platform's, stops before it starts when the editor has not enabled that platform, and says how to: with **Enable Platform** in Unity's Build Profiles window, which applies to one user, or with `-enableAllDerivedPlatforms` on the editor's command line, as on a build machine. Unity built such a profile with its build target's settings instead of the profile's, Android's for Meta Quest, without an error, so a build machine's builds lacked the profile's Debug Symbols, for example. Where Build Forge cannot tell whether the platform is enabled, because a Unity version lacks the lookups it uses for that, the build stops as well and says so
- In a project linked to Unity Cloud, a build with the Cloud Diagnostics plugin on left `ProjectSettings/UnityConnectSettings.asset` with crash reporting as the build had it: setting it back reached the editor but not the file, so the next build took the changed value for the project's. The plugin now puts the file back byte for byte after the build
- On Unity 6000.7, every build failed after Unity had built the player, with "Saving restored settings to disk failed", and a command-line build exited with an error: 6000.7 keeps a Build Profile's own Player Settings in a sub-asset instead of the embedded copy Build Forge refreshed. Build Forge now saves the sub-asset. Where an editor has neither, it still saves the restored settings before it reports the failure
- When Build Forge cannot undo the applied profile's settings before a build, the build still stops, but the settings it had already undone are applied again, so the editor is left as it was. They used to stay undone, which the build window showed as drift from the applied profile
- Addressables Stripper: from Addressables 4.1 it leaves an excluded group out through the group's own Include in Build, so Content Directory groups are excluded too. It only knew the setting of the Content Packing & Loading schema, which they don't have, so a Content Directory group ticked under Exclude Groups shipped anyway, while the build window and the manifest said it was excluded. Before 4.1, the exclusion of a group without that schema stops the build
- Addressables Stripper: an exclusion that names a group or label the project doesn't have, after it was renamed or removed, stops the builds that use it, and the profile's settings list it as not found, with Remove. Such an exclusion excluded nothing, without a word, and the settings didn't show it
- OpenXR: a build also puts back the OpenXR settings that the inspector hides, such as the multiview render regions mode, which Unity's Meta Quest build step copies from Meta Quest Support's settings. Only visible settings were snapshotted, so such a value stayed in the OpenXR package settings after the build, and a profile's override of one carried over to later builds of other profiles. Values OpenXR derives itself, such as the custom loader, stay out of the snapshot. A profile applied to the editor before this update can show OpenXR drift once; Re-apply, or any build, clears it
- OpenXR: overrides and pinned feature settings that OpenXR can't take any more, after an update renamed or removed a setting or a feature, or with a value the setting can't read, stop the profile's builds and Apply before anything changes, and the profile's OpenXR section lists them with Remove. They were skipped, some without a word, a pin of an asset that is gone cleared the reference, and the manifest still listed them as applied. The section also lists, with Remove, settings overrides that its Settings list doesn't show: of a setting OpenXR hides, or of one a feature controls
- Addressables Stripper: its temporary group is named `BuildForge Excluded (do not delete)`. It was named as safe to delete, but after a crash during a build it holds the entries the Stripper moved out of their groups, and deleting it deletes them. The crash-recovery steps also name `Assets/AddressableAssetsData/` and the manifest the Android Manifest plugin swaps in
- On Unity 6000.7, the Player Overrides window shows the overrides of a Build Profile that has its own Player Settings. 6000.7 keeps them in a sub-asset instead of the embedded copy the window read, so it showed such a profile as using the project's settings

## [0.9.3] - 2026-10-16

### Added
- `IForgeEditorApplicable.MergeEditorState`, optional: the snapshot that undoes an Apply after its settings changed, keeping those changes. Without it, Build Forge restores the baseline then and warns that this may undo them

### Fixed
- Undoing an Apply no longer undoes changes made to its settings since, such as a git pull's. Revert to Baseline, Re-apply, Activate and every build while a profile is applied restored the settings from before the Apply. A build then used those old values and wrote them back into the project, where they could be committed over a teammate's change. Now each OpenXR setting, feature state and XR Management value goes back only where it still has the value the Apply wrote. **Dismiss Drift** takes the accepted changes into the baseline, so reverting later keeps them

## [0.9.2] - 2026-10-16

### Added
- **OpenXR Features** under Play Mode Follows Applied Profile in Project Settings > Build Forge, shown while it is on. **Turn on the platform's**, the default, turns on Standalone's OpenXR features that the applied platform has on and turns none off, so features Standalone has on for Play Mode itself, such as hand tracking for a tool that authors hand poses, stay on. **Match the platform's** also turns off those the platform has off, as applying always did before. To keep such a feature out of a Standalone build, give that profile a Disable override

### Changed
- **Play Mode Follows Applied Profile** is off by default. A project keeps the value its `ProjectSettings/ForgeSettings.asset` stores. With it on, OpenXR features now default to **Turn on the platform's**; choose **Match the platform's** for the previous behavior
- **Maintain Build Profile Defines** is off by default, so Build Forge writes no `BUILD_PROFILE_<NAME>` define into a Build Profile unless asked: turn it on in Project Settings > Build Forge > Profiles to use the define. A project keeps the value its `ProjectSettings/ForgeSettings.asset` stores
- `ForgePluginAttribute.SafeToDefaultEnable` is renamed `EnabledByDefault`, which says what it does: whether the plugin starts enabled in Project Settings > Build Forge > Installed Plugins. A plugin that sets `SafeToDefaultEnable = false` now sets `EnabledByDefault = false`. The plugin manual states the rule behind it: installing a plugin must not change any build until a profile turns the plugin on or configures it
- Project Settings > Build Forge lists the installed plugins by name, instead of in the order builds run them
- OpenXR's Meta Quest setup for batch builds is off by default, with a **Meta Quest Setup** switch in each Meta Quest profile's OpenXR foldout. With it on, a build of the profile turns on the features OpenXR 1.18 turns on in the editor, while `ProjectSettings/BuildProfileUtilityOpenXR.asset` says that step hasn't run, as before. With it off, the build window and the build log warn when the profile's builds would lack them

### Fixed
- Changing a plugin's settings in a profile or in Project Settings and then changing them back, such as an OpenXR feature set to Enable and back to No Override, no longer leaves the plugin's settings in the Build Profile asset or in `ProjectSettings/ForgeSettings.asset` with only default values. `ForgeProfile.SetPluginConfig` and `ForgeSettings.SetGlobalPluginConfig` remove a configuration whose values equal a new instance's, as they remove null, so the file is left as it was
- The build window's platform icons match Unity's Build Profiles window: the details header shows the platform's large icon at its 32 points instead of the small one scaled up, on the window's rounded icon background, darker than the pane in the dark theme and lighter in the light one, and on a high-DPI display the list, the header and the main toolbar use the icons' high-resolution textures, as Unity's windows do
- The build window's details header lines its subtitle up with the profile's name above it, instead of slightly to its right
- A Platform Player Overrides matrix cell's tooltip shows the cell's value without the column's name in front, which the header shows, and no longer ends with "Click to select the Unity Build Profile.", which the legend says. A profile's cell still adds its platform's Project Settings value

## [0.9.1] - 2026-10-15

### Added
- Public API for plugins, which the bundled plugins now use too: `GitHelper` runs git in the project, `BuildProfileUtility` gives a Build Profile's build target, `BuildEnvironment.IsCI` the CI detection a build would see, outside a build, `ForgeSettings.IsPluginEnabled(Type)` whether a plugin is on in Project Settings, and a plugin that assigns the build number can set `ForgeBuildContext.BuildNumber`, which `{BuildNumber}` and the manifest read
- The Package Manager links to the manual and to this changelog on GitHub (`documentationUrl`, `changelogUrl`)
- **Build** and **Build and Run** in the main toolbar's Build Forge element, next to the profile and apply dropdowns. They build the active profile like the build window's Build, with the variant the window has selected, which picking a variant in the apply dropdown also sets; **Build and Run** then runs the build like Unity's Build And Run, without showing it in the file browser. Disabled when the window's Build would be, with the reason as their tooltip. They show the build window's icons: the Build Forge anvil on Build, Unity's Play icon on Build and Run
- **Build and Run** in the build window's action bar, next to Build and green like it, with Unity's Play icon: builds the active profile like Build, then runs it like Unity's Build And Run, without showing it in the file browser

### Changed
- Once a project has variants, every build names one of them; a project without variants builds without one. The default build, the build without a variant beside them, is gone. A command-line build without `-forgeVariant` in a project with variants fails and lists the variants rather than picking one. The build window and the main toolbar have no `<default>` entry; they start on the applied variant, and until a variant is applied or picked, Apply and Build wait for one. `default` is no longer reserved: `Default` is an ordinary variant name, marked like any other. Restrict Variants must allow at least one variant. In the API, `ForgeBuildRunner.RunBuild` without a variant throws in a project with variants, `ForgeBuildContext.Variant` is null only in a project without variants, and `ForgeProfile.SupportsVariant` no longer accepts `Default` on its own. To keep a project's builds as they were, add a variant named `Default`, so `BUILD_VARIANT_DEFAULT`, the `Default` output folder, the manifest's `Default` and the `Default` Variant Rule and Addressables Stripper entries stay as they are; set that rule's Mark Product Name to **Disabled** (add the rule if there is none); add `Default` to the Allowed Variants of profiles that restrict variants; and pass `-forgeVariant Default` in CI commands that passed no variant
- Variant names may contain only letters (in any alphabet), digits, spaces, `-` and `_`, must start with a letter or digit, and must not be a device name Windows reserves (`CON`, `NUL`, `COM1` and the like): a name is a folder in the output path and an argument on the command line. Other names are a configuration error until the variant is renamed
- Every bundled plugin compiles into an assembly of its own against the public API only, as a user's plugin does: Build Number, Git Metadata, Cloud Diagnostics, Android Keystore Env, Android Manifest and XR Vendor Filter moved out of `BuildForge.Editor` into `BuildForge.Editor.BuildNumber`, `.GitMetadata`, `.CloudDiagnostics`, `.AndroidKeystoreEnv`, `.AndroidManifest` and `.XRVendorFilter`. Build Profiles and `ProjectSettings/ForgeSettings.asset` saved before this name the old assembly for these plugins' settings, which then show their defaults, and editing them replaces what was saved: in each `type:` line of their config classes, change `asm: BuildForge.Editor` to the plugin's assembly

## [0.9.0] - 2026-10-07

The first internal release.

### Added
- Build Forge settings are stored inside their Unity Build Profile, as a Build Profile component in the profile's `.asset` (Unity 6.3+ component API), so they share its name and file, and renaming, duplicating or deleting the Build Profile carries them. They are edited in a "Build Forge" section of the Build Profile editor (the Build Profiles window, and the Inspector for a Build Profile asset), which also adds and removes them, and from Assets > Build Forge (several Build Profiles at once) or the Build Profile inspector's context menu; the Assets > Create menu no longer makes separate profile assets
- Per-profile **Remove Previous Build Output** option, on by default for new and existing profiles, with an Inspector warning when off; applies to editor and CI builds. Before each build it removes the artifact file and the files the previous build of that profile and variant produced (recorded per user in `UserSettings`); files that were already in the destination, or changed since, are kept. No old APK, AAB or Windows/Linux executable survives a later failure (a macOS .app bundle and directory outputs are cleaned only from the build record); unsafe output directories are rejected, and the build stops when the destination cannot be read or a file cannot be deleted
- Generated CI commands use `unity run` for project-version lookup, with reserved launcher flags omitted and Accelerator upload waiting enabled. Subfolder project paths start with `./`, so Unity CLI does not read them as registered project names. Direct Editor entry points remain supported.

The build rejects `-forgeBuildProfile` and points to Activate. The build window's CI Command shows both commands, **One workspace per job** and **Shared workspace** (Activate, then the build); the sample scripts take `-SharedWorkspace` and `--shared-workspace`, and the sample Jenkins pipeline and GitHub workflow, which build any profile in one workspace, activate before every build
