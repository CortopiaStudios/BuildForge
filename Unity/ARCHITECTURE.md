# Build Forge — Architecture & Design Decisions

This document captures the architectural decisions, technical learnings, and design principles behind Build Forge. It exists so that future contributors (or the original authors returning after a break) can understand *why* things are the way they are without re-discovering hard-won knowledge.

## Design Principles

### Don't duplicate what Build Profiles do well
Build Profiles handle scenes, scripting defines, build options, and Player Settings natively. Early versions of Build Forge duplicated scenes, defines and build options; those were removed because Unity's own handling of them is enough. Player Settings are a different case. A Build Profile overrides them with a full copy of every setting instead of the fields it changes, so what a profile changes is opaque, and its copy goes stale when Project Settings change. Build Forge's per-field override editor was removed because replicating Unity's whole Player Settings system seemed too much work while Unity's profile overrides offered a shortcut, not because per-field overrides lacked value. Relying on Unity's overrides has its own cost: Build Forge builds and maintains the visibility Unity doesn't provide, the diff view and the Player Overrides matrix. Variant rules still set some Player Settings for their builds (Build Configuration, the version string, the product name). Build Forge focuses on the gaps: plugin-managed settings (OpenXR, XR loaders, vendor clean-up), per-variant build settings, build manifests, build interception, and Player Settings visibility.

### One Build Forge Profile per Unity Build Profile
A Unity Build Profile belongs to exactly one Build Forge Profile. The Unity profile is the identity Unity itself acts on (active profile, scripting defines, Player Settings), so under 1:1 it identifies the Build Forge configuration too: the CI entry point resolves the Build Forge Profile from the active Build Profile (`-activeBuildProfile` is the only argument needed), and a scripting define on the Unity profile can stand for the whole configuration. `ForgeProfileLookup` holds the rule; sharing is an error in the profile inspector and the build window (the profile cannot be selected, applied or built), and CI resolution aborts on none or more than one, never a silent pick. Named variants can vary development options, defines and variant-aware plugin behavior within that pair. Separate pairs are needed when the underlying native profile configuration differs (for example scenes or platform settings). Everything user-facing therefore uses the Unity Build Profile's name (`ForgeProfile.DisplayName`: the build window, the `{ProfileName}` output-path placeholder, the manifest's `BuildProfileName`, the scripting define); the Build Forge asset's own name (`ProfileName`) appears only in messages about the asset itself, such as "no Unity Build Profile assigned" or the shared-profile error. The rule also holds if Build Forge data is ever embedded in the Build Profile as a component (one instance per type), so nothing built on it is lost by that decision.

### Plugins own their own settings
Plugin-specific settings (both per-profile and global) are owned by the plugin, not by the core `ForgeSettings` class. A plugin defines a plain `[Serializable]` config class and stores it per profile with `ForgeProfile.GetPluginConfig<T>(key)` / `SetPluginConfig(key, config)`, or globally with `ForgeSettings.instance.GetGlobalPluginConfig<T>` / `SetGlobalPluginConfig` (`ProjectSettings/ForgeSettings.asset`). Both are version-controlled. The object is held as a `[SerializeReference]`, so it serializes as ordinary YAML fields — a profile change is a one-line diff, reviewable in a PR — rather than an opaque string (the original JSON-string store was replaced for exactly that reason). Contract: `Get` returns the stored instance, or a fresh default that is *not* stored (reading never dirties an asset); after mutating, call `Set` again so the asset is dirtied; never share one instance between profiles; re-`Get` rather than cache. If a plugin's package is removed, Unity keeps the managed-reference data (with an "Unknown managed type referenced" warning) and restores it when the type returns. Unity writes every serialized field, including ones the current mode ignores (Addressables `cleanBeforeRebuild` when no rebuild is requested, a keystore env var name whose mode is Inherit), so a reader sees defaults there — not configuration that was applied. Fields with a fallback getter (Build Number `envVarName`, the global keystore env var names, the profile's `outputPath`) have no initializer for that reason: they store empty until the user types a name, so a value in the YAML always means someone chose it. `EditorPrefs` is only appropriate for per-user UI preferences (window state, expand/collapse, last-selected items) that don't affect builds; one that belongs to a single project lives in `UserSettings/ForgeUserPreferences.asset` instead (the main toolbar's visibility). This means third-party plugins don't need to modify core code to add their own settings.

### Forward-compatible where possible
Prefer runtime discovery over hardcoded lists. OpenXR settings are discovered via `SerializedObject` iteration. Integer-backed enums are resolved via reflection on `PlayerSettings`. Per-platform properties in the diff view are detected by content (platform name keys) rather than property name lists. New Unity versions should mostly "just work."

### Correct comparison over suppression
When false positives appear in the diff view, fix the comparison rather than maintaining a suppression table. The diff view's accuracy comes from three normalization steps applied during comparison: YAML single-quote un-escaping (`''`→`'`), null-reference canonicalization (`{instanceID: 0}`→`{fileID: 0}`), and whitespace collapsing. A small structural-metadata filter (`productGUID`, `serializedVersion`, `m_Script`, `m_ObjectHideFlags`, `clonedFromGUID`) handles fields that are never meaningful overrides. No per-version data is needed — the diff view works correctly on any Unity version with no maintenance. See Development~/LEARNINGS.md for the history of the per-version defaults table that this approach replaced.

### Safe defaults for output paths
`Application.productName` is set by humans for display purposes ("My Awesome Game: Reloaded") but ends up in file paths via the `{ProjectName}` placeholder. Spaces break unquoted shell commands in CI scripts. Colons are invalid in Windows paths. Apostrophes and parentheses trip up tools like `adb push`, `fastlane`, and `steamcmd`. Rather than forcing users to discover these failures one at a time, Build Forge sanitizes the product name by default (`ForgeSettings.MangleForFilename`). The setting is on by default but can be disabled in Project Settings for teams that want the raw product name.

The mangling rules are intentionally conservative: `&` becomes `and` (preserves meaning), punctuation is removed (`:'"!.()`), everything else non-alphanumeric becomes `_`, and consecutive separators are collapsed. Non-ASCII letters (accented characters, CJK) are left as underscores since they can cause issues with some build tools and CI systems, even though modern filesystems support them.

### UI clarity
- Disabled plugins are hidden from profile inspectors (managed only in Project Settings)
- Plugin sections start collapsed and persist expand state via `SessionState`
- The diff view uses rich rendering (color swatches, thumbnails, enum names) but stores/compares raw YAML
- The build window auto-discovers profiles rather than requiring manual selection

## Core Architecture

### Build Runner (`ForgeBuildRunner`)
The central orchestrator. Uses `BuildPipeline.BuildPlayer(BuildPlayerWithProfileOptions)` — the Unity 6 profile-aware API — so the Build Profile handles scenes, player settings, defines, and build options natively. Build Forge wraps this with:

1. Removing the previous build's recorded output when the profile's Remove Previous Build Output option is on, after profile/variant validation and before plugin discovery or preparation
2. The variant's development flags, Build Configuration and scripting define on the Build Profile (the Build Configuration's IL2CPP and stripping settings in Player Settings), and the marked product name
3. Plugin `OnPreBuild` hooks
4. The variant rule's Version, after the hooks so `{BuildNumber}` is the number Build Number set
5. Manifest writing
6. `BuildPipeline.BuildPlayer()`
7. The version restored, plugin `OnPostBuild` hooks (in `finally` — guaranteed execution), then the variant settings and product name restored: undo runs in reverse order of apply, so a plugin that snapshots a setting in `OnPreBuild` restores it before the variant is undone
8. Manifest cleanup

The profile's `RemovePreviousBuildOutput` setting (Inspector: Remove Previous Build Output; serialized as `removePreviousBuildOutput`, which still reads the former `pruneBuildDestination` field) defaults to true, including when loading older assets without the field. It deletes files, never folders wholesale: only what a build of the same Unity Build Profile and variant is known to have produced. After every build that reaches the runner, successful or not, `BuildOutputDirectory.Record` stores what the build produced in the per-user `BuildOutputLedger` (`UserSettings/ForgeBuildOutputs.asset`, keyed by Build Profile GUID and variant): every file and folder new in the destination since the listing taken just before the build, plus report entries there whose size or write time changed, as relative paths with size and write time. An unchanged report entry is never recorded (a failed build's report lists source files, which can lie inside a broad destination), and nothing below a folder that could not be read before the build is. That listing fails closed: an unreadable destination aborts the build. Before the next build, `BuildOutputDirectory.Prepare` deletes the artifact file (APK, AAB or Windows/Linux executable; the exact file the build writes, recorded or not, so a failed build never leaves an old one) and then each recorded file that is still inside the destination, not below a link, nested Unity project or checkout inside it, outside protected folders, not recorded by another profile or variant in the same destination, and unchanged in size and write time; then the recorded folders that are now empty. The destination is never removed. A macOS `.app` bundle and directory outputs are cleaned only from the record. Without a record (first build, fresh CI workspace) only the artifact file is deleted; after a destination change the previous build's files are removed from where they were recorded, unless that place is missing, offline, or inside another Unity project or Git checkout (found by walking up from it on disk and stopping at the first folder that holds this project, so the project's own repository counts as ours however Git spells it, nested or not, or with Git unavailable), and a file there that cannot be deleted is only reported. Switching an Android profile from APK to export removes the APK that would block the export folder; switching back removes the export folder only when it holds nothing but the export's own files, and otherwise the build stops before it starts, naming the folder (Unity itself would fail only after the Gradle build). Each record names the project folder it was made in, and records from another folder are dropped: a duplicated project copies `UserSettings`, and the copy must never clean the original's output. Records of Build Profiles or variants that no longer exist are dropped too, and another profile's record protects a file only while it still matches that file, so stale records stop protecting files. While the recorded destination is missing, unreadable or its volume is offline (a share, an unplugged drive, a folder behind an unmounted link, a link whose target is gone), nothing is removed and its record is kept until a build records its own output, rather than read as all files gone; after a destination change the new destination's record replaces it, since there is one record per profile and variant. An entry whose reparse tag cannot be read before the build counts as unreadable, so it cannot look new afterwards. Destinations that contain the project or repository root, lie inside a Unity project's own folders (found on disk, so a junction to this project is caught too) or `.git`, are a Unity project or checkout themselves, overlap the package source or the editor installation, or are a filesystem root are rejected. A file that cannot be deleted aborts the build; it and the files after it stay recorded, while files skipped as changed, shared or unsafe leave the record. Links at or above the destination are allowed: the build writes through them, so deleting through them hits the same files, and projects under a junction or a redirected Documents folder must build. On Windows only name-surrogate reparse points (symbolic links, junctions) count as links, so cloud-file placeholders such as OneDrive's are ordinary files; the reparse tag is read with the `\\?\` prefix because Unity is not long-path aware, and short (8.3) names are expanded wherever paths are compared, for the project and the other roots as well as the destination. On FAT volumes, which store local time, a write time shifted by exactly one hour (a daylight-saving change) still counts as unchanged. The residual risk is a file that lands in a shared destination during a build: it is recorded and removed next time if unchanged. When disabled, the runner neither deletes nor records and logs that existing files may remain. The setting applies to every variant of that profile. Uploads must still require success: the option being off or errors before the runner (including Unity compilation and CLI argument validation) can leave old artifacts, and player failures can leave partial new artifacts. See "BuildReport.GetFiles() Is Not the Build's Output" for why the record cannot come from the report alone.

The key value over Unity's native `IPostprocessBuildWithReport`: the `finally` block attempts every plugin's restoration even when the build throws. Unity's post-process hook does not run on build failure. Restoration and cleanup errors are recorded in `PostBuildFailures`; CI exits unsuccessfully even if the player artifact was built successfully.

The runner snapshots `PlayerSettings.GetPreloadedAssets()` immediately before the native player build and restores the complete list in `finally`, before Forge post-hooks. This removes temporary native/XR additions when Unity skips its postprocessors, preserving legitimate assets and order, including additions owned by Forge plugins. Restoration failures join `PostBuildFailures` and do not prevent the remaining cleanup.

The generated CI command uses `unity run` because Forge requires the native profile selected at startup (before compilation) and its own execute method. In standalone CLI 1.0.0-beta.9, `unity build` rejects `--profile` combined with `--execute-method` and also rejects forwarding `-activeBuildProfile` through `--args`. These CLI checks fail before launching either Editor; they were verified on Windows on 2026-09-16 with invocations targeting the 6000.3.0f1 and 6000.6.0f1 test projects, and 1.0.0-beta.11 still rejects both (2026-09-29, 6000.3.23f1 project). `unity run` permits both arguments. See the README's CI section for the exact errors and the condition for revisiting this choice.

CLI owns `-batchmode`, `-projectPath` and `-quit`; Forge keeps the entry method and plugin hooks synchronous and explicitly exits only after saving restored settings. Required work must finish before a hook returns. Deferred callbacks and async-void hooks cannot provide this contract. CLI normalizes Editor failures to a nonzero launcher status; consumers must treat any nonzero result as failure. `-cacheServerWaitForUploadCompletion` allows pending Accelerator uploads to finish during shutdown. Crashes and forced timeouts still cannot guarantee managed cleanup.

Forge's own arguments are parsed strictly (`ForgeBuildRunner.ParseCommandLine`), because an argument the entry point ignores still yields a successful build of the wrong thing. An argument starting with `-forge` that Forge does not take (a typo, or the removed `-forgeProfile`) and a Forge argument without a value (last on the line, followed by another flag, or empty, as an unset CI variable produces) fail with exit code 1 before any build work; names match case-insensitively. `-forgeVariant Default` is the explicit spelling of the default build. Every Forge argument carries the prefix, which is what makes a misspelling detectable among Unity's own arguments; `-versionCode` was renamed `-forgeVersionCode` for that reason and is refused with a pointer to the new name.

When manifest writing is enabled, a write failure aborts the build. The StreamingAssets injector also fails the build if the required manifest has disappeared before injection. When disabled, it ignores any stale manifest left in `Library/`.

### Plugin System
Plugins implement `IForgePlugin` and are marked with `[ForgePlugin]`. Discovery uses `TypeCache.GetTypesWithAttribute<ForgePluginAttribute>()` — zero-config, O(1) at editor startup.

Plugin lifecycle:
- `IsApplicable(BuildProfile)` — should this plugin run for this profile?
- `NotApplicableReason(BuildProfile)` — short sentence shown in the profile inspector explaining why `IsApplicable` returned false (e.g. "Only applicable to Android build profiles."). Defaults to null, which renders a generic message
- `IsEnabled(ForgeProfile)` / `SetEnabled(ForgeProfile, bool)` — the per-profile enable switch. `IsEnabled` defaults to null, meaning "no on/off switch" (plugins that are merely unconfigured stay null). When non-null, Build Forge owns the enable UX end to end: the profile inspector renders the "Enabled" checkbox (persisting via `SetEnabled`) and grays out the plugin GUI, the foldout header shows "(disabled)", and the build runner skips the plugin's hooks when false — plugin hooks need no enabled guard of their own
- `Description` — one-line summary of what the plugin does; shown as a tooltip when hovering the plugin's name in plugin lists (profile inspector, Project Settings, Build window). Defaults to null (no tooltip)
- `Validate(ForgeProfile)` — return warnings shown in the build window (e.g. Player Settings overrides may shadow plugin writes)
- `OnPreBuild(ForgeBuildContext)` — apply settings, store state for restoration
- `OnPostBuild(ForgeBuildContext)` — restore settings (runs in `finally`)
- `OnDrawProfileGUI(ForgeProfile)` — per-profile config UI in the inspector
- `OnDrawSettingsGUI()` — global settings UI in Project Settings

Plugins that contribute data to the build manifest also implement `IForgeManifestContributor`:
- `ContributeToManifest(BuildManifest, ForgeBuildContext)` — add a section to the manifest

Plugins whose overrides are meaningful as persistent editor state (settings-shaped plugins like OpenXR — never build numbers, signing or symbol upload) also implement `IForgeEditorApplicable` (see "Editor State" below):
- `CaptureEditorState(BuildTargetGroup)` — JSON snapshot of everything the plugin may write for the group, or null when there is nothing to manage
- `ApplyToEditor(ForgeProfile, BuildTargetGroup)` — write the profile's overrides and save
- `RestoreEditorState(BuildTargetGroup, string)` — write a snapshot back and save

The group is passed explicitly because a third-party plugin cannot derive it from a non-active Build Profile, and because the Unity Build Profile is activated *after* these calls — implementations must use group-explicit APIs, never active-profile statics.

Plugins are sorted by `IForgePlugin.Order` (lower runs first). `OnPostBuild` hooks run in reverse order, so plugins that modify settings early get restored late.

Each bundled plugin has its own multiple of 100, so the bundled plugins always run in the same order; orders 1–99 remain available for external plugins that need to run before any bundled plugin:

| Order | Plugin | Category | Rationale |
|-------|--------|----------|-----------|
| 100 | XR Loaders | XR settings | Selects ordered providers before OpenXR settings and content generation |
| 200 | OpenXR | XR settings | Applies features after loader selection and before content generation |
| 300 | Git Metadata | Read-only | No side effects — reads git state and writes to manifest |
| 400 | Build Number | PlayerSettings | Modifies `bundleVersionCode` / `buildNumber` |
| 500 | Cloud Diagnostics | Project settings | Toggles `CrashReportingSettings.enabled` (and with it symbol upload) per environment |
| 600 | Android Keystore Env | PlayerSettings | Overrides keystore/key alias from env vars |
| 700 | Addressables Stripper | Addressables | Toggles IncludeInBuild flags — must run before Rebuild |
| 800 | Addressables Rebuild | Addressables | Rebuilds content with stripping already applied |
| 900 | Android Manifest | Project files | Swaps in the profile's main manifest for the build |
| 1000 | XR Vendor Filter | Android packaging | Last, so its Gradle-step leftover check sees what every other plugin's Gradle step left |

Variant options are resolved before these hooks. Loader and OpenXR settings are applied before content generation. Addressables stripping must precede rebuilding because IncludeInBuild flags affect generated bundles. External plugins pick an order between these values; plugins with the same order run in no defined order.

Plugins communicate via `ForgeBuildContext.SetProperty/GetProperty` — a typed key-value store scoped to a single build.

### CI Detection (`ForgeBuildContext.IsCI`)
Some work is only worth doing on a build machine — uploading symbols is the canonical example. Rather than each plugin inventing its own "am I in CI?" heuristic, the context carries one answer resolved by `BuildEnvironment`: `-forgeCI [true|false]` on the command line wins, then the `FORGE_CI` environment variable, then `Application.isBatchMode`. `ResolveIsCI` reads an unrecognized `-forgeCI` value as a bare `-forgeCI` (true) and ignores an unrecognized `FORGE_CI`; the CLI build fails on either instead (`BuildEnvironment.ValueError`), since both would turn a mistyped "false" into a CI build. An empty `FORGE_CI` still counts as unset. Batch mode is the right default (the `CommandLineBuild` entry point always runs in it), and the overrides cover the two cases where it's wrong: local scripted builds that shouldn't count as CI, and interactive CI agents that should. Plugins that expose an environment-dependent setting should use an explicit Always / CI only / Never mode (see Cloud Diagnostics) so the local and CI outcomes are both visible in the inspector, rather than a boolean that silently means different things on different machines.

### Build Profile Defines (`BuildProfileDefines`)
Compile-time identification of the profile is delegated to Unity: each referenced Build Profile carries a `BUILD_PROFILE_<NAME>` entry in its own Scripting Defines list, which Unity applies in the editor and the build whenever that profile is active. No baseline or revert is needed because nothing global is mutated, and the define is committed with the profile. Build Forge writes it whenever it touches the profile (inspector, build window refresh, profile switch, always deferred out of the GUI pass) and replaces a stale prefixed entry after a rename; anything without the prefix is the user's. A write to the *active* profile requests a script compilation so the editor domain picks it up; so do the variant define writes of Apply, Revert to Baseline and Activate, through the same `BuildProfileDefines.RequestScriptCompilation`. On early 6000.3 patches the `BuildProfile.scriptingDefines` setter does not update Unity's record of the defines it last compiled (`BuildProfileContext.cachedEditorScriptingDefines`), and Unity's Build Profiles window, when it shows the active profile, compares the two as its settings go away (at the recompile's domain reload, for one) and asks to apply or revert: Revert writes the old defines back and undoes Build Forge's change. There the request also makes Unity's own internal `BuildProfileModuleUtil.RequestScriptCompilation(profile)`, which updates that record; it is found by reflection, skipped when missing, and a test fails on an editor that needs it but lacks it. Later setters update the record themselves (checked: 6000.3.0f1 does not, 6000.3.23f1 and 6000.6.0f1 do; a batch probe compared the record with the profile right after each Apply, Revert and Activate). The build runner never writes (that would recompile mid-build) and only warns. `ForgeSettings.MaintainBuildProfileDefines` turns the writes off. The prefix is what makes rename cleanup safe: only exact-prefix entries are Build Forge's. Sanitizing is lossy (a Build Profile name is a file name; a define is a C# identifier), so two names can map to one define; non-ASCII letters are kept to reduce that, which was verified on 6000.3.23 and 6000.6.0 (a Build Profile with `BUILD_PROFILE_ÜBUNG` saves, activates, and satisfies the `#if`); `CollisionWarning` flags that in the build window and inspector because the collision is invisible inside Unity (each define lives in its own profile) and only shows up as an `#if` that is true for both.

### Build Variants (`BuildVariants`)
A variant remains one project-wide selector with strict CLI resolution and optional per-profile restrictions. Optional rules own development options, a Build Configuration (IL2CPP, stripping, compression, Android link-time optimization and debug symbols), the version string, aliases and product marking; projects without rules retain their existing behavior. The Build Configuration's per-platform Player Settings are recorded as Unity's serialized maps and written back as recorded: setting a platform's default value through the API adds a map entry, which would leave `ProjectSettings.asset` changed after every build. The runner resolves options and defines before plugins, Addressables and manifest generation. Editor iteration persists the selected variant's defines, never its development flags: the flags do not reach editor compilation (the editor never gets `DEVELOPMENT_BUILD`), and written to a committed Build Profile they reached every machine without the committer's ledger, where a Default build inherited them (verified with real players on 6000.3.0f1 and 6000.6.0f1). A per-user ledger records only what Build Forge changed, so undoing it (Revert, a variant switch, the start of a build) keeps edits made to the Build Profile since Apply. A `BUILD_VARIANT_` define on a Build Profile that is not applied on this machine can only have been saved while a variant was applied elsewhere (committed while applied, or saved by a build that did not finish); the build window, the profile inspector and the build log report it, and Activate removes it together with the rules' aliases, as every build does. Builds restore temporary changes and any previously applied editor variant after success or failure. Output directories and manifests retain the variant identity; application identifiers are unchanged. See [Variants and XR loader selection](Development~/VARIANTS-AND-XR.md) for the contracts and executable proof.

### Editor State (`ForgeEditorState`)
The build path applies overrides transiently. The build window's "Apply \<profile\>" applies them persistently so Play Mode matches a profile. Activation is a separate step ("Activate \<profile\>" = Unity's Switch Profile, preceded by a revert of anything another profile applied so nothing stale remains; the applied profile itself keeps its settings and variant define, which are exactly its deltas); Apply is enabled for the active profile when it has editor-applicable settings or configured variants; once applied, Re-apply remains available even after overrides are removed — and persistent mutation is only safe with an invariant: **applied editor state = baseline + one profile's deltas, never stacked on the previous profile.** Overrides are deltas ("No Override" means "inherit the global value"), so without that invariant every No-Override hole in profile B would silently inherit whatever profile A left behind.

The model: while a profile is applied, `ForgeEditorStateStore` (`UserSettings/ForgeEditorState.asset` — per user, in Unity's default `.gitignore`, survives `Library/` deletion) holds the GUID of its *Unity* Build Profile (the Build Forge profile is resolved through the 1:1 lookup, so "applied" is a property of Unity's profile and the ledger survives a future embedding of Build Forge data into it) and one entry per participating `plugin|BuildTargetGroup` — `baselineJson` (the state before Build Forge touched that group) and `expectedJson` (the state right after applying). `EditorStateApplier` is the pure core over those lists (fully unit-tested with fake plugins); `ForgeEditorState` binds it to the singleton, the registry, the asset database and the Build Profile system, and is the only entry point for the UI and the build runner.

- **Apply(B)**: restore every existing entry to its baseline in reverse order, removing only successful entries (this is "revert A", and it works even if A's asset is gone). If any restore fails, persist the remaining baselines, keep A's identity and variant, and stop before applying B; otherwise checkpoint-save; for each participating pair: `baseline := Capture`, `Apply`, `expected := Capture`, record; save; **last**, activate B's Unity Build Profile — that call may trigger a domain reload, and everything is already on disk by then. Baselines are captured fresh on every apply, right after the previous profile is reverted, so they are never stale and hand edits made while nothing is applied are preserved automatically.
- **Revert to Baseline**: attempt every restore in reverse order and remove successful entries. Failed entries and their baselines are saved for retry; the applied GUID and variant are cleared only after all restores succeed. Activate also stops on a failed revert. An entry whose cause is permanent (its plugin's package was removed, or its baseline names an XR loader that no longer exists) would block every Apply, Activate, revert and build, so after a failed Revert the window lists what failed and offers **Stop Tracking** (`ForgeEditorState.StopTracking`): the remaining entries, which are exactly the unrestored ones, are dropped with the applied GUID and variant, and those settings keep their current values. Nothing is dropped automatically, since a package that is only temporarily missing (a branch switch, a failed resolve) would lose its baseline. With the editor closed, deleting `UserSettings/ForgeEditorState.asset` is the last resort; it forgets every baseline. **Dismiss Drift**: `expected := Capture` (baselines and the profile asset untouched; the next apply or build resets it) — for legitimate drift such as an OpenXR package upgrade rewriting feature metadata.
- **Drift** = any entry whose current capture differs from `expected` (string compare; captures sort their lists). Configuration edits do not change this snapshot comparison, so Re-apply is always available for an applied profile. Cached for two seconds because capturing serializes every OpenXR feature and the build window repaints ~10 Hz. Known drift-by-design sources: Unity's Meta Quest profile type auto-enabling controller profiles on domain reload (invisible by default because interaction profiles are excluded from the managed scope unless `ShowInteractionProfileOverrides` is on), and Meta's `OVRGradleGeneration` rewriting plugin importer state.
- **Builds**: `ForgeBuildRunner` suspends the applied profile (restores baselines, keeps entries) before the pre-build loop whenever a profile is applied — *including* when the built profile is the applied one, because the profile asset may have been edited since it was applied (an override changed to No Override leaves the old value in the editor, and drift detection cannot see that since the editor state did not move). Suspension attempts every entry; any failure aborts the build before its plugins or player build run, retaining the ledger for recovery. After successful suspension, the runner resumes the applied profile in `finally`. Each successfully re-applied and captured entry updates its expected snapshot; a failed entry keeps its baseline and previous expected snapshot so drift remains visible. Resumption attempts the remaining entries and reports failures through `PostBuildFailures`, causing CI to fail even when the artifact succeeded.
- **Active vs. applied**: "active" is Unity's state (its active Build Profile; the window shows it as an "Active" tag on the row) and "applied" is Build Forge's (the ledger). They diverge whenever Unity switches profiles without Build Forge (its own Switch Profile button, `-activeBuildProfile`) or a platform profile becomes active (Unity's Platforms list, `-buildTarget`, a deleted `Library/`, which keeps no active Build Profile; `BuildProfile.GetActiveBuildProfile()` is null then): the active profile's Player Settings then run on top of the previously applied profile's plugin settings. `GetActiveMismatch` reports that in the build window and the main toolbar with the fixes: Apply the active profile (unless no Build Forge Profile references it, which is always so for a platform profile), activate the applied profile again, which keeps its settings, or Revert to Baseline. Build Forge's own Activate never creates this state, because it reverts another profile's settings first. Building in that state is still correct, because builds always suspend the applied profile and run from the baseline, so Build stays available.
- **Guards**: apply/revert/accept are refused in Play Mode (the OpenXR `enabled` setter silently refuses while its loader runs, and platform switches are disallowed), during compilation or import, and during builds. The UI invokes them through `EditorApplication.delayCall`, never inside OnGUI.
- **Why the ledger is per-user, not in `ForgeSettings`**: the applied profile is the analog of Unity's active Build Profile, which Unity also keeps local (`Library/EditorUserBuildSettings.asset`), and the two must stay coherent — a committed ledger would tell a teammate "Quest is applied" while their editor is on another profile, and a Revert would restore settings they never applied. It would also churn and conflict on every apply. The trade-off: applying still mutates committed assets (`Assets/XR/Settings`, inherent to persistent switching), so committing *while applied* commits those in the applied state with no ledger to explain it — CI and teammates then build on that state wherever a profile leaves a setting at No Override. The build window warns while a profile is applied; revert to baseline before committing settings assets unless the applied state is intentional. The planned coverage lint closes the No-Override holes that make this matter.
- **Play Mode XR**: Play Mode runs on Standalone's XR settings whatever the active platform, so an applied Android profile's plugin settings never reach it by themselves. With `ForgeSettings.PlayModeFollowsAppliedProfile` on (the default), `GetParticipatingPairs` appends one `<mirror>|Standalone` pair per `IForgePlayModeMirror` after the plugins' pairs, for a profile of any other group: `PlayModeXRLoaders` (XR Management assembly) copies the platform's active loaders, minus those whose XR Management metadata excludes Standalone, and Initialize XR on Startup; `PlayModeOpenXRFeatures` (OpenXR assembly) copies the on/off state of every feature type both groups have, interaction profiles included, and nothing else. The mirrors are found through `TypeCache`, not the plugin registry, so no plugin list shows them, and `ResolvePlugin` falls back to them, so Revert, drift, suspension for builds and resumption treat their entries like a plugin's. They run last on Apply and resume, so they copy the platform as the plugins left it, and first on revert. Verified in a game project on 6000.6.4f1: Apply of its Quest profile turned on Standalone's Foveated Rendering and Composition Layers, which its Android settings had on, left out the Android-only features, and Revert to Baseline restored the settings byte for byte.
- **Crash mid-apply**: each entry with its baseline is checkpoint-saved to `UserSettings/ForgeEditorState.asset` before its plugin writes (plugins flush their own assets — OpenXR calls `SaveAssets` — so the ledger must hit disk first), so "Revert to Baseline" is a one-click recovery.

The OpenXR plugin's capture/apply/restore is one shared core (`OpenXRSettingsState`) used by both the build path and the editor path; the baseline/expected snapshot covers all simple top-level `OpenXRSettings` properties plus the full serialized state of every managed feature. One consequence beyond editor application: the post-build restore now also undoes the top-level values Unity's `MetaQuestFeatureBuildHooks` pushes during a build. The same hook overwrites a profile's settings override of `m_symmetricProjection`, `m_optimizeBufferDiscards` or `m_spacewarpMotionVectorTextureFormat` with MetaQuestFeature's value (seen on a Quest 3, whose OpenXR diagnostics reported symmetric projection off). The inspector hides settings a feature declares, so `Validate()` and pre-build warn about any such override, which can only come from hand-written YAML; the feature pin is the form that works. Snapshot feature JSON comes from `EditorJsonUtility`, which writes asset references as `{fileID, guid, type}` (verified on 6000.3.23 and 6000.6.0) — session-stable as is, so no instance-ID handling is needed or wanted: the instance-ID APIs are obsolete-as-error from 6000.3.23 and `EntityId` loses its int conversions in 6000.6. That JSON stays JSON because it is machine-compared for drift and never reviewed. The *profile's* per-feature settings, by contrast, are stored as readable property pins: `SerializedPropertySnapshot` (Editor/Core) flattens the native editor's feature copy into `(propertyPath, value)` leaves — every visible property, so applying is independent of whatever is globally set at edit time and a pin to a default value is expressible — and `OpenXRSettingsState.SkipFeatureProperties` excludes the `OpenXRFeature` base metadata (`nameUi`, `version`, `featureIdInternal`, …). Applying writes them back through `SerializedProperty`.

Not yet covered: a coverage lint warning when a profile leaves a setting at No Override that another profile overrides. (The XR Plug-in Management loader list is covered by the XR Loaders plugin.)

### Main Toolbar (`ForgeMainToolbar`)
Build Profile and apply dropdowns in Unity's main toolbar, registered with the official `[MainToolbarElement]` API (Unity 6.3+) as one element, `Build Forge` (the path is also its name in Unity's toolbar menu and drag tooltip), with no dock position of its own: it appears where Unity docks new elements (the attribute's default, the left section), users move it with Ctrl+drag, and Unity keeps the position (machine-wide, see below). The profile dropdown calls `ForgeEditorState.Activate`; the apply dropdown calls `ForgeEditorState.Apply` for the active profile, with the picked variant when variants exist and plain Apply or Re-apply otherwise, and `RevertToBaseline` (offering the window's Stop Tracking after a failed revert) whenever anything is applied (`HasAppliedGuid`), the active profile or another, like the window's Revert to Baseline button. So they behave exactly like the build window's Activate, Apply and Revert to Baseline, from `delayCall` like the window's actions, and applying from the toolbar also makes the window select that variant. The wording follows the window as well: the apply label is the window's Editor line in short ("Applied, drifted (Internal)", drift from `GetDrift`), and the tooltips reuse the window's Activate, drift and mismatch texts (`GetActiveMismatch`, `UnresolvedAppliedWarning`). The apply dropdown shows while its menu offers something: an apply, when the window would enable Apply for the active Build Forge Profile (it is applied, variants exist, or it has editor-applicable plugin settings), or a revert. The element is disabled whenever `CanMutate` refuses. Its labels show state that also changes without Build Forge (Unity's own Switch Profile, Project Settings, drift), so a once-a-second comparison of a key (the active Build Profile's path, the applied Build Profile and variant, the drift keys while the active profile is applied, the variant list, the mutate reason) calls `MainToolbar.Refresh`, and asset changes reset the key. Only the drift part costs anything: `GetDrift` captures every applied plugin's settings at most every two seconds, about 2.5 ms per capture in the OpenXR test host on 6000.6.0f1 (0.2 ms for OpenXR, 2.3 ms for XR Loaders), and the key asks for it only while the active profile is applied. The menus are built when opened, from pure functions with tests.

Visibility is the part the API does not cover: Unity starts every package toolbar element hidden; only its own elements, tagged with the internal `UnityOnlyMainToolbarPreset` attribute, start visible, and `MainToolbarElementAttribute` has no default-visibility option ("display by default" is a TODO in its source up to `master`, checked 2026-09-29). Build Forge therefore finds its overlay through the public `EditorWindow.TryGetOverlay` with the element path as id, the same lookup `MainToolbar.Refresh` makes (6000.3, 6000.6 and `master`), and sets the public `Overlay.displayed` from `ForgeUserPreferences.ShowMainToolbar` (true by default) whenever a new overlay instance appears; the overlay's `displayedChanged` event records Hide or Show from Unity's toolbar menu. The preference lives per user and project in `UserSettings/ForgeUserPreferences.asset`, beside Build Forge's other per-user state, so it survives a layout reset; Unity's own record is in the layout (`UserSettings/Layouts/`), seeded from a machine-wide copy in the Preferences folder. If Unity ever changes the id scheme, the element simply stays hidden, Unity's default. Verified interactively on 6000.3.0f1 and 6000.6.0f1: on a fresh clone a control element without this logic stayed hidden while Build Forge's showed; a Hide persisted across launches, deleting `UserSettings/Layouts` kept the recorded choice, and the labels followed a change of the variant list without a domain reload. A walk through the editor states showed the expected labels and tooltips on both: Apply with a variant and with the default variant, a drifted setting, Re-apply, Unity switching to another Build Profile and then to the platform profile without Build Forge (the apply dropdown stayed, offering the revert, until Revert to Baseline), and the same without variants. Unity 6.6 caps a toolbar dropdown's text at 120 px and cuts longer labels with an ellipsis ("Applied (Development)" becomes "Applied (Developm…"); 6.3 has no cap. The labels keep the state first so it stays readable, and the platform-profile label is "Platform profile" (it names what is active, like the warnings, and fits). Adding UI to the toolbar outside this API is explicitly unsupported (Unity 6.3 logs a warning for it), so it was not considered. Batch mode has no toolbar, and nothing runs there.

### Plugin Default States
All discovered plugins are enabled globally by default in Project Settings. This makes sense for plugins installed by the user (e.g. OpenXR, Addressables) — if you installed the package, you want its plugin active. The global toggle is an escape hatch, not the primary activation mechanism.

Bundled plugins require more nuance because they're present whether the user wants them or not. The default state depends on the plugin's impact:

- **Git Metadata** — defaults to enabled globally, enabled per-profile. Low risk: only writes to the build manifest, doesn't modify project settings.
- **Build Number** — defaults to enabled globally, **disabled per-profile**. Modifies `Android.bundleVersionCode` and `iOS.buildNumber` during the build, which affects store submissions and CI versioning. Users must opt in per profile.
- **Cloud Diagnostics** — defaults to enabled globally, **disabled per-profile**. Sets `CrashReportingSettings.enabled` for the duration of the build (default mode: CI only). Enabling crash reporting is what triggers Unity's automatic IL2CPP symbol upload, so this both skips the upload for local builds and keeps local crashes out of production diagnostics. Note the coupling: a build with crash reporting off neither uploads symbols nor reports crashes — there is no Unity switch for one without the other.
- **Android Keystore Env** — defaults to enabled globally, **disabled per-profile**. Overrides the Android keystore path and password, key alias and key password from environment variables at build time (`ANDROID_KEYSTORE_PATH`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` by default; the names follow Gradle's `storeFile`, `storePassword`, `keyAlias` and `keyPassword`, not Unity's `keyaliasPass`). Only applicable to Android builds. Does not duplicate signing settings — Unity's existing PlayerSettings and Build Profile overrides are the first two tiers; this plugin adds env var overrides as a third tier for CI. If an env var is not set or the env var name is empty, the existing value is left untouched — but a var that is *set and empty* (a failed CI secret), a custom keystore with an empty path, or signing vars present with no custom keystore in play (silently debug-signed output) fail the build before any settings are touched. Default env var names are configured globally in Project Settings; individual profiles inherit them but can override per field.
- **Addressables Rebuild** — defaults to enabled globally, **disabled per-profile** (its enable switch is stored in the config's historical `rebuildBeforeBuild` field). No action without explicit opt-in.
- **Addressables Stripper** — defaults to enabled globally, but requires explicit group/label configuration per profile. No action without configuration.

The principle: a fresh install should never change build output without the user explicitly enabling it. Manifest-only contributions are safe to default on. Anything that modifies PlayerSettings or build artifacts defaults to requiring per-profile opt-in.

### Player Settings Diff View
Compares a Build Profile's Player Settings against the platform defaults using YAML-to-YAML comparison. This was the result of several iterations:

1. **First attempt**: SerializedProperty comparison — failed because Build Profiles store player settings as `m_PlayerSettingsYaml`, a YAML blob stored as an array of byte-encoded lines, not a structured SerializedProperty tree.
2. **Second attempt**: Parse YAML to dictionary, compare against SerializedProperty — failed because serialization formats differ (YAML: `{fileID: 0}`, SerializedProperty: `0` for null refs; YAML: `{r: 0.5, ...}`, SerializedProperty: JSON for colors).
3. **Final approach**: Parse both the Build Profile YAML and `ProjectSettings/ProjectSettings.asset` YAML, compare YAML-to-YAML. Same format, no conversion, handles all property types.

**YAML parsing**: Uses a line-based parser (`UnityYamlParser`) that extracts top-level key-value pairs by indentation. Unity's serialized YAML is non-standard (unterminated quoted scalars, tagged object references, etc.) so a spec-compliant YAML parser cannot reliably handle it. The line-based approach is robust for this use case since we only need top-level property names and their values as text.

### Build Manifest
Written to `Library/BuildForge/Manifest/BuildManifest.json` and handed to the build through a `BuildPlayerProcessor` calling `BuildPlayerContext.AddAdditionalPathToStreamingAssets` (the mechanism Unity's Adaptive Probe Volumes use), so it lands at `StreamingAssets/BuildForge/BuildManifest.json` in the player while the project's Assets folder is never touched: nothing to import, no `.meta` churn, nothing for version control to see, no cleanup that can go wrong. The original design created the file under `Assets/StreamingAssets` and deleted it afterwards; see "Files Deleted Behind the Asset Database" under pitfalls for why that broke in batch mode on 6000.6. On Android and WebGL, `BuildManifestLoader` uses `UnityWebRequest` since StreamingAssets lives inside the APK / behind an HTTP URL. The package declares the UnityWebRequest module rather than leaving it optional: without it, Android and WebGL players of a project that disabled the module failed to compile Build Forge's runtime. The synchronous `Load()` is unsupported on WebGL because a fetch cannot complete without yielding to the browser. Concurrent `LoadAsync` callers share one in-flight `Task` (an `Awaitable` can only be awaited once), and the cache flags are published only after the load finishes. Readable at runtime via `BuildManifestLoader.Load()` / `LoadAsync()`. Plugins contribute sections via `IForgeManifestContributor`.

### Conditional Plugin Assemblies
The OpenXR, Addressables and XR Loaders plugins live in separate assemblies with `defineConstraints` and `versionDefines` in their `.asmdef` files. The OpenXR assembly also references the XR Loaders assembly; the OpenXR package depends on XR Plug-in Management, so the two compile together. When the required package isn't installed, the assembly simply doesn't compile. No `#if` guards needed in source files. The settings provider shows "Available Plugins" with install buttons for packages that aren't yet installed.

### OpenXR Feature Groups Are Not Supported (by design)
Unity's OpenXR package has "Feature Groups" (internally `OpenXRFeatureSet`) — editor-only groupings defined via `[OpenXRFeatureSet]` attributes that bundle multiple features for a target device (e.g., "Meta Quest Support"). A group can declare features as Required (force-enabled, checkbox grayed out), Default (auto-enabled on first activation, user can disable), or Optional (just shown in the filtered list).

Build Forge deliberately does not replicate the feature group abstraction. Reasons:

1. **Feature groups are keyed by `BuildTargetGroup`, not Build Profile.** `OpenXREditorSettings` stores which groups are enabled as `Dictionary<BuildTargetGroup, List<string>>`. Multiple Build Profiles sharing a `BuildTargetGroup` (e.g., Quest 2 and Quest 3 are both `BuildTargetGroup.Android`) share the same group state. This is the exact limitation Build Forge exists to solve — adding a group layer on top would inherit the same per-`BuildTargetGroup` constraint from Unity's side.

2. **Individual feature overrides are strictly more powerful.** Build Forge overrides features at the individual level (Enable / Disable / No Override per feature, or an allow-list with Only Listed Features, which turns every unlisted visible feature off and leaves hidden ones to their packages). Anything a feature group can express, individual overrides can express too. The reverse is not true — you can't use groups to enable Feature A from one group while disabling Feature B from the same group.

3. **Groups add complexity without capability.** Replicating the group system would require re-implementing `OpenXRFeatureSetManager.SetFeaturesFromEnabledFeatureSets` logic (three-tier membership, union semantics across groups, transition tracking for default features). This is significant surface area for zero additional power over individual overrides.

4. **Groups are a vendor convenience, not a user modeling tool.** They exist so Meta/Pico/etc. can ship a single attribute that lights up the right features. Users building per-device profiles in Build Forge are already past that — they know which features they want per profile.

If users want the mental model of "this profile uses Meta Quest features," the equivalent in Build Forge is configuring the individual feature overrides once on that profile. The feature list is discoverable in the inspector and forward-compatible via `SerializedObject` iteration.

Ticked groups are actively hostile to per-profile overrides, not just redundant: `OpenXRFeatureSetManager.SetFeaturesFromEnabledFeatureSets` force-enables every *required* feature of a ticked group, `OpenXRFeature.enabled = false` on such a feature is silently refused (`CanFeatureBeDisabled`), and the OpenXR package re-runs the force on every domain reload while a Meta Quest platform profile is active. The OpenXR plugin's `Validate()` therefore warns whenever any group is ticked for the profile's target group, and names the profile's Disable overrides that a group blocks. The build stops on those rather than shipping a feature the profile disables: after applying, pre-build checks that every managed feature took its override, and for a Disable that a ticked group refused, the error names the group. (The groups themselves — "Meta XR" from the Meta XR Core SDK, "Meta Quest" from Unity OpenXR Meta — come from other packages; the OpenXR package defines none of its own.)

### Interaction Profile Overrides Are Hidden by Default
OpenXR interaction profiles (controller bindings) are not exclusive — multiple can be enabled simultaneously, and the OpenXR runtime selects the appropriate one based on connected hardware. The recommended workflow is to enable all supported profiles globally in XR Plug-in Management.

Unity's own Meta Quest build profile type auto-enables three Meta controller profiles on domain reload via `BuildProfileUtility.OnLoad()` (guarded by `#if UNITY_META_QUEST`). Its "run once" flag lives on a `ScriptableSingleton` without `[FilePath]`, so it is recreated after every domain reload and the hook runs *every* time, not once. This means switching to a Quest build profile adds profiles to the global settings automatically — and Build Forge can't prevent that without fighting Unity's own initialization code. When interaction profile overrides are shown and a Meta Quest platform profile is active, the OpenXR plugin's `Validate()` warns about any Disable override on those three profiles, since the hook undoes it in the editor. (`UNITY_META_QUEST` is the only reliable signal: the Meta Quest platform GUID is defined in native code and not exposed.) OpenXR 1.18 replaced this with `BuildProfileUtilityOpenXR`, whose flag is saved (`isMetaQuestInitialized` in `ProjectSettings/BuildProfileUtilityOpenXR.asset`): it enables the three controller profiles and Meta Quest Support for Android once while a Meta Quest Build Profile is active, and on the first editor load without one it turns them off again and clears the flag. That runs on a delayed call, which batch builds never reach, so a project whose Quest profile becomes a plain Android profile builds correctly in CI until someone opens it in the editor (seen in a real project, where Oculus Touch for Android went off). The OpenXR plugin warns about an Android profile, in `Validate()` and in the pre-build log, while the flag is set and no Meta Quest profile is active; it reads the flag by reflection and stays silent on OpenXR versions without that step (1.16.1 has none). The opposite case is a batch build of a Meta Quest profile while the flag is clear, as in a CI checkout where the file was committed as 0 or not at all: an editor would enable the features on load, so `OnPreBuild` enables the ones that are off itself (the utility's `metaFeatureIds`, read by reflection), and the post-build restore undoes it, interaction profiles included. With the flag set it leaves them alone, because OpenXR already did its part and any later change was the user's.

Per-profile interaction profile overrides exist for the rare case where a team needs to exclude vendor-specific profiles from a build (e.g., contractual reasons, or using a generic Android build profile instead of the Meta Quest type to avoid the auto-add behavior). The setting is off by default (`OpenXRGlobalConfig.ShowInteractionProfileOverrides`, stored via the global plugin config mechanism) so the UI stays focused on features and settings, which are where per-profile differentiation actually matters.

### XR Vendor SDKs in Other Vendors' Builds

An Android project that ships to several headsets has every installed XR vendor SDK in every Android build. In 2026-10 builds (Meta Core and Platform SDK 205, Pico OpenXR 1.4.1), the sources were:

| Source | Adds | Can a profile prevent it? |
|---|---|---|
| Meta Core SDK `OVRGradleGeneration` (IPostGenerateGradleAndroidProject, order 99999) calling `OVRManifestPreprocessor.PatchAndroidManifest` | The Oculus VR launch category (always), supported devices and focus awareness (whenever `OVRProjectConfig` targets any Quest), splash, telemetry and Horizon OS SDK entries (`OVRProjectConfig`) | No: unconditional, and its config is one asset for all profiles |
| Meta Platform SDK `ModifyAndroidManifest` (order 1) | The Horizon OS supplement | No: unconditional |
| Meta Platform SDK `libovrplatformloader.so`, Pico `libpxrplatformloader.so`, Meta's OVRPlugin, Steamworks.NET `libsteam_api.so` | Native libraries, and the manifest inside any AAR | Yes: Unity's include-in-build delegate |
| Pico `PlatformManifestRewrite` (order 9999) | Pico entries | Only by clearing the Pico app ID, a project-wide setting |
| A project's custom main manifest | Whatever it declares | Yes: a per-profile manifest |

The Oculus XR plugin, Pico's own AAR processor and Unity's MetaQuestFeature already gate their content on their loader or feature.

So the XR Vendor Filter prevents what can be prevented and removes the rest. `XRVendorFilterPreprocess` (IPreprocessBuildWithReport at 1000000) sets `PluginImporter.SetIncludeInBuildDelegate` on the excluded packages' Android libraries after the vendors' own pre-build steps, which set delegates on some of the same importers (Meta's on OVRPlugin at order 3). The delegate returns false only while the build that excludes them runs, and true otherwise, so it is left in place: Unity offers no way to read or restore the previous delegate, and the vendors set theirs again in every build's pre-build step. Only native and Java libraries are excluded (`.aar`, `.jar`, `.so`, `.java`, `.kt`, `.androidlib`); managed assemblies stay, because game code may reference them.

The manifest entries are removed in Build Forge's Gradle step (`ForgeGradleCallback`, IPostGenerateGradleAndroidProject at 1000000, after Meta's 99999), which forwards to the build's `IForgeGradleProcessor` plugins in plugin order; the XR Vendor Filter has order 1000, the highest bundled one, so its leftover check runs after every other plugin's Gradle step. The step edits the source manifests of the Gradle project and skips Gradle's `build` folders, which hold earlier builds' merged manifests, and Unity's `assets` folder. The leftover check also opens the manifest of every remaining `.aar`, because Gradle merges those after the step has run. A library file name that an included library shares (two packages' `libopenxr_loader.so`) is not reported as a leftover.

The Gradle callback only compiles when `UNITY_ANDROID` is defined (`UnityEditor.Android` exists only with Android support installed); a Build Forge build always has its profile's platform active, so Android builds have it.

## Known Limitations

### Editor crash during build can leave settings in an overridden state
Plugins like OpenXR, Build Number, and Android Keystore Env modify project settings in `OnPreBuild` and restore them in `OnPostBuild`. The restore runs in a `finally` block, so it survives build failures and exceptions. However, if the Unity editor crashes or is force-killed mid-build, `OnPostBuild` never runs and the overridden values remain on disk (plugins call `SaveAssets()` to flush changes because `BuildPipeline.BuildPlayer` reads from disk).

**Why we don't auto-recover:** Persisting pre-mutation snapshots to a temp file and restoring them on the next editor launch is technically possible but not worth the complexity. It would require serializable snapshot formats per plugin, partial-state handling (crash after plugin 3 of 6), false-recovery guards (editor killed for an unrelated reason), and is extremely difficult to test. The recovery code itself would be a source of bugs.

One part is recoverable without version control: while a profile is applied to the editor, the per-user ledger (`UserSettings/ForgeEditorState.asset`) keeps every applied group's baseline across the build, so "Revert to Baseline" restores those settings (today OpenXR and the XR loader list) after a crash. Build-time-only overrides (build number, keystore, crash reporting) have no ledger. Neither has the variant a build applies to the Unity Build Profile: its defines and development flags can reach disk mid-build when a plugin saves assets, and after a crash the variant ledger (`UserSettings/ForgeVariantDefines.asset`) treats them as the user's own edits, so Revert keeps them. With nothing applied, a variant define left that way is reported like one committed from another machine, and Activate removes it with the rules' aliases, but not the development flags. Restore the Build Profile asset from version control in that case.

**Recovery:** If settings look wrong after a crash, restore the affected files from version control:
```
git checkout -- ProjectSettings/
```
For OpenXR settings (stored under `Assets/XR/`), also restore those:
```
git checkout -- Assets/XR/
```
For a variant build, also restore the Unity Build Profile asset that was built, for example:
```
git checkout -- "Assets/Settings/Build Profiles/"
```

Editor crashes mid-build are rare. Version control is the safety net. (If a profile was applied to the editor at the time, "Revert to Baseline" in the Build window restores the pre-apply state of the plugin-managed settings — see "Editor State".)

## Technical Pitfalls & Learnings

### YAML Structure of Build Profiles
Build Profiles store player settings as YAML-within-YAML:
```yaml
m_PlayerSettingsYaml:
  m_Settings:
  - line: '| PlayerSettings:'
  - line: '|   companyName: MyCompany'
  - line: '|   bundleVersion: 1.0'
```
Each `- line:` entry contains the actual YAML prefixed with `'| '`. Multi-line values (colors, object references) can span multiple `- line:` entries. The parser must join continuation lines before extracting key-value pairs.

### Object References in YAML
Two formats exist:
- `{fileID: N, guid: hex, type: N}` — persistent asset references (used in `.asset` files)
- `{instanceID: N}` — runtime/session-local references (used in Build Profile YAML)

Both `{fileID: 0}` and `{instanceID: 0}` mean null/unassigned but must be normalized for comparison. Non-zero `fileID` references are resolved via `AssetDatabase.GUIDToAssetPath()` + `TryGetGUIDAndLocalFileIdentifier()`.

### Per-Platform Dictionary Properties
`ProjectSettings.asset` stores some properties as per-platform dictionaries (e.g. `scriptingDefineSymbols`, `applicationIdentifier`, `scriptingBackend`). Global and profile YAML can contain different sets of platforms. The diff selects entries for the selected profile's build target before comparing, including Unity's platform aliases and complete `m_BuildTarget` / `first` sequence blocks. Differences for other targets are ignored; differences in identifiers, backends, stripping settings and other selected-target values remain visible. A missing entry is displayed as `(default)` rather than assuming a platform-specific value. A Dedicated Server profile (Standalone build target, `m_Subtarget` Server) is compared on Unity's `Server` entries (`NamedBuildTarget.Server`), not the Standalone ones. `m_BuildTargetBatching` is split into Static Batching and Dynamic Batching rows only after the target's entry is selected; split first, the rows would show whichever platform's entry came last.

### Integer-Backed Enums
Unity serializes some enums as `SerializedPropertyType.Integer` rather than `SerializedPropertyType.Enum`. Examples: `fullscreenMode`, `meshDeformation`, `activeInputHandler`. The diff view resolves these via reflection on `PlayerSettings` C# properties, matching by name (case-insensitive) to find the backing enum type.

### SerializedProperty.enumValueIndex vs intValue
`enumValueIndex` returns the index into Unity's display-sorted enum names, NOT the raw backing integer. Always use `intValue` to get the actual enum value when comparing or storing.

### GUIUtility.ExitGUI() and Layout Groups
Calling `GUIUtility.ExitGUI()` inside a `BeginHorizontal`/`EndHorizontal` pair throws an `ExitGUIException` that skips `EndHorizontal`, corrupting IMGUI's layout stack. Solution: defer actions (adds, removes) until after the layout loop completes.

### BuildPipeline.BuildPlayer() Inside OnGUI
Calling `BuildPipeline.BuildPlayer()` from within `OnGUI` corrupts the IMGUI layout state. Solution: wrap in `EditorApplication.delayCall`.

### Files Deleted Behind the Asset Database
Creating a file under `Assets/`, building, then deleting it with `File.Delete` and exiting (a CLI build) leaves Unity's stores with stale state for that path. On 6000.6.0 the Unity Data Store (`Library/DataStore`) reconciled that state during the next build's first asset refresh by silently deleting the recreated file — between preprocess callback orders 1 and 3, blocked only by making the file read-only, invisible to a `FileSystemWatcher`, path-specific (`Other/BuildManifest.json` survived, `BuildForge/BuildManifest.json` did not), and gone once `Library/DataStore` was removed. In the editor an auto-refresh after the deletion kept the stores consistent, which is why only CI builds lost the manifest. Rule: never create-and-delete files under `Assets/` around a build; hand extra StreamingAssets content to the build through `BuildPlayerContext.AddAdditionalPathToStreamingAssets` from a `Library/` folder instead, as the manifest now does.

### Object References Do Not Survive a Build
A `UnityEngine.Object` reference held in C# across `BuildPipeline.BuildPlayer` can come back as Unity's fake null: the build's unload-unused-assets pass destroys loaded assets that nothing native references. Observed in batch mode on 6000.6.0 with the `ForgeProfile` the build suspension held for the resume, which then read as "the applied profile no longer exists" and cleared the ledger. Rule: across a build, hold GUIDs or paths and resolve again afterwards, never the object (`ForgeEditorState.ResumeAfterBuild` re-resolves through the ledger).

### BuildReport.GetFiles() Is Not the Build's Output
Probed on 6000.3.0 and 6000.6.0 (Windows Mono, IL2CPP and development players; APK, AAB and Android export). For a successful Windows build or an Android export the report lists every file Unity writes to the destination, including the IL2CPP backup folder and StreamingAssets added through `BuildPlayerContext`. It never lists files that packages write themselves in post-build steps (Meta XR Core copies `RuntimeActionBindings.json` next to Windows players without overwriting, so a leftover copy makes its step throw; OpenXR 1.18 API layers, the Autodesk FBX runtime and Unity Localization on iOS write there too), and Unity offers no public API to add them. On both editors it omits the IL2CPP backup folder Unity writes next to an APK or AAB, and on 6000.3 with Burst 1.8 the Burst debug-information folder next to a player. Android reports, successful or not, also list hundreds of intermediate files under `Library/Bee` (a failed Android build does list the APK it wrote), and on 6000.3 a Windows player build that fails after writing its output reports only source paths, in the editor installation and `Library`, and none of the files it left in the destination. Rule: never delete from a raw `GetFiles()` list. Keep only report entries inside the destination whose size or write time changed since a listing taken just before the build, and add every file new since that listing, as `BuildOutputDirectory.ComputeRecord` does; that listing must fail closed, because a folder it could not read would make everything in it look new.

### Asset Save Timing
Unity doesn't serialize Inspector edits to disk immediately; a dirtied asset is written on Save Project, before some reloads, and on quit. The diff view calls `AssetDatabase.SaveAssetIfDirty()` before reading a Build Profile's `.asset` file to flush pending changes. Build Forge Profiles get the same treatment on the writing side: the profile inspector schedules `SaveAssetIfDirty` (via `delayCall`, out of the GUI pass, one write per frame at most) whenever the profile is dirty after a GUI pass, so the `.asset` file matches the Inspector and the readable-YAML goal holds for git diffs too. `ForgeSettings.SaveProfilesOnEdit` (Project Settings > Build Forge > Profiles) turns this off for projects where the extra write per edit is a problem.

### ScriptableSingleton.Save() Is Protected
`ForgeSettings` extends `ScriptableSingleton<ForgeSettings>`. The `Save()` method is protected, so it can't be called from outside the class. Exposed via a public `SaveSettings()` wrapper.

### Unity Writes Explicit Values After Touch-and-Restore
When a user toggles a setting (e.g. static batching) and toggles it back, Unity writes the explicit value to the Build Profile instead of reverting to the empty representation (`[]`). When both sides serialize the same explicit value, normalization removes representation noise such as whitespace and null-reference encoding. An absent per-platform entry and an explicit value can still appear as `(default)` versus that value: the YAML comparison does not resolve Unity's implicit defaults.

### YAML Single-Quote Un-Escaping
Build Profiles wrap each player-settings line as a YAML single-quoted scalar, doubling any inner quote (`'` → `''`). Extracting content without un-escaping produces values that differ from the same value in `ProjectSettings.asset`. Fix: `.Replace("''", "'")` on extraction. See Development~/LEARNINGS.md for the full story of how this one-line fix eliminated an entire per-version defaults infrastructure.

### Null-Reference Canonicalization
`ProjectSettings.asset` uses `{fileID: 0}` for null references. Build Profile YAML uses `{instanceID: 0}`. Both mean null. The canonicalization must happen inside the whitespace-collapsed string (not just at the top level) to catch null refs nested in structs.

### SerializeReference Config Storage
Plugin configs live in `[SerializeReference] object` slots (`PluginConfigSlot`). Unity's rules: the instance must be a `[Serializable]` class — not a struct, not a `UnityEngine.Object`, no dictionaries — or it serializes as a null reference and silently vanishes on reload; `SetPluginConfig` throws for those cases. Unity writes managed references in a `references:` block with persistent `rid`s (assigned once, so unchanged slots don't churn). `SerializedObject.ApplyModifiedProperties` in the profile inspector never touches these slots, so the plugin-owned instances are not clobbered by the inspector's property fields. Renaming or moving a config class makes it a "missing type" (data preserved, warning logged) — use `[MovedFrom]` after 1.0.

### Feature Property Pins Use NextVisible
`SerializedPropertySnapshot` iterates with `NextVisible`, not `Next`: hidden fields (`[HideInInspector]` migration flags, obsolete fields kept for upgrades) are not pinned, because pinning them across package upgrades is a hazard and they are not what the user edited. `Color` properties are one leaf (`r,g,b,a`) because `NextVisible` does not descend into a color's channels, while vectors, rects and bounds do decompose into visible leaves.

### Float Parsing and Locale
`float.TryParse` without `CultureInfo.InvariantCulture` fails silently on comma-decimal locales (sv-SE, de-DE). Always use `NumberStyles.Float, CultureInfo.InvariantCulture` for any float that touches serialization, YAML comparison, or cross-machine data.

### Static Fields Reset on Domain Reload
Cross-platform builds trigger a domain reload mid-build. Any static field used as a flag (e.g., `IsForgeBuildInProgress`) resets to its default. Use `SessionState.GetBool/SetBool` for state that must survive domain reloads within a session.

### Git Process Deadlock
`ReadToEnd()` before `WaitForExit(timeout)` makes the timeout meaningless — `ReadToEnd` blocks until the child closes stdout. With `RedirectStandardError = true`, an undrained stderr pipe can deadlock. Fix: read stdout/stderr asynchronously, then `WaitForExit`, then `Kill()` on timeout, and always `Dispose()`.

### Addressables Stripping Requires an In-Build Content Rebuild
The stripper's changes (IncludeInBuild flags on excluded groups; entries with an excluded label moved into a temporary non-built group, since removing the label alone would leave the asset packed and loadable by address) are applied in OnPreBuild and reverted in OnPostBuild — they are transient. Content built *before* the player build (e.g. a manual Addressables build) always contains the excluded content. Exclusions therefore require a content build *during* the pipeline: the Addressables Rebuild plugin (Order 800, after the stripper's 700) or Unity's "Build Addressables on Player Build" = Build With Player. The stripper fails the build when exclusions are configured without either guarantee; the per-user editor preference (PreferencesValue) is deliberately not honored because content correctness must not depend on machine-local state. Per-variant exclusions are keyed by variant name, like Variant Rules and Allowed Variants, so a rename orphans them; the stripper fails every build of the profile while an entry names an unconfigured variant (which variant it was meant for is unknown, and the renamed one has no entry), and the inspector offers to move or remove it.

### Console "Clear on Build" Hides Pre-Build Logs
Unity's Console has a "Clear on Build" option (enabled by default). When `BuildPipeline.BuildPlayer` runs, it clears the console — wiping all pre-build plugin logs. Only post-build logs (from the `finally` block) survive. This can make it look like `OnPreBuild` never ran. Disable "Clear on Build" in the Console toolbar to see the full log sequence.

### Static PlayerSettings API Targets the Active Profile
When a Build Profile has Player Settings overrides, Unity's native `GetPlayerSettings()` function returns the profile's override instance. Since all `PlayerSettings.Android.*` / `PlayerSettings.iOS.*` static API calls go through `GetPlayerSettings()`, they automatically read and write the active profile's settings — not the global singleton. This means plugins can use the static API directly without needing `SerializedObject` or reflection to access per-profile values.

Persistence needs an additional step: the profile keeps an embedded YAML copy separately from its live PlayerSettings object. `AssetDatabase.SaveAssets()` alone can save stale build-time overrides even after the static API has been restored. `PlayerSettingsPersistence` re-resolves the active profile after the build, invokes Unity's internal `BuildProfile.SerializePlayerSettings()` to refresh that copy, marks the profile dirty, and saves. This runs after plugin restoration and editor-state resumption, and again after restoring CLI `-forgeVersion` / `-forgeVersionCode` overrides. The internal serializer is verified on 6000.3.0f1 and 6000.6.0f1; if unavailable or failing, restoration is reported as a failure rather than allowing a successful CI exit.

The same holds for `EditorUserBuildSettings.buildAppBundle` (verified empirically on 6000.3: it follows `SetActiveBuildProfile` immediately, follows live edits of the active profile's checkbox, and ignores edits to non-active profiles — and gradle's `bundle*`/`assemble*` task selection obeys the same value). The codebase convention: use active-profile-tracking statics wherever the code path guarantees the profile is active (`RunBuild` enforces this); read serialized profile fields (`BuildProfileUtility.GetBuildTarget`) only when querying **non-active** profiles, where no static can answer.

### GUIStyle Allocations in OnGUI
Creating `new GUIStyle(...)` in `OnGUI` allocates garbage every frame. Cache as `static` fields initialized once with `??=`.

## Public API Surface

Everything not listed here is `internal` — implementation detail, free to change between releases. Tests access internals via `InternalsVisibleTo`: the core assembly grants it to the test assemblies and the bundled plugin assemblies (`Editor/AssemblyInfo.cs`), and the OpenXR and Addressables plugin assemblies to their own tests.

**Runtime** (game code): `BuildManifest`, `ManifestSection`, `ManifestEntry`, `BuildManifestLoader`.

**Extension contract** (third-party plugin authors): `IForgePlugin`, `IForgeManifestContributor`, `IForgeEditorApplicable`, `IForgeGradleProcessor`, `ForgePluginAttribute`, `ForgeBuildContext` (received, not constructed — the constructor is internal), `ForgeProfile`, `ForgeSettings` (global plugin config storage).

**Scripting/CI**: `ForgeBuildRunner.RunBuild`, `ForgeBuildRunner.GetCICommand`, `ForgeBuildRunner.IsForgeBuildInProgress`, the constants `ForgeBuildRunner.ForwardedCIArguments` and `StaticCIArguments` (compiled into callers, so a change reaches them only when they recompile), `BuildForge.CommandLine.Build` (the `-executeMethod` entry point; resolves the Build Forge Profile from the active Unity Build Profile), `BuildForge.CommandLine.Activate` (activates the Unity Build Profile given to `-forgeBuildProfile`, in a run of its own before a build that changes platform).

The bundled plugins and their configs, all UI types, and the core machinery (`ForgePluginRegistry`, `BuildManifestWriter`, `UnityYamlParser`, `PlayerSettingsDiffComputer`, `GitHelper`, …) are deliberately internal: exposing a type later is an additive, non-breaking change — the reverse is not.

## Roadmap Context

### Player Settings Override System (removed, may return)
A per-field Player Settings override editor was built and then removed: replicating Unity's whole Player Settings system seemed too much work while Unity's Build Profile overrides offered a shortcut. See Development~/LEARNINGS.md for the full story. If re-implemented, the rule would be: Build Forge Player Settings are only available when the Unity Build Profile has no Player Settings of its own — one source of truth.

### Build Profile Components (evaluated, not adopted)
Unity 6.3 added a public component API on `BuildProfile`: `AddComponent<T>`, `CreateComponent<T>`, `GetComponent<T>`, `RemoveComponent<T>`, and static `GetActiveComponent<T>`. A component is a `ScriptableObject` stored as a sub-asset of the profile `.asset` (`AssetDatabase.AddObjectToAsset`, `HideInHierarchy`), one instance per type. Unity 6.4 added `[BuildProfileSettingsProvider(typeof(T))]` + `BuildProfileSettingsProvider`, which is how packages like Platform Toolkit get an "Add Settings" entry and a foldout in the Build Profiles window.

Build Forge stores a `ForgeProfile` inside its Unity Build Profile as such a component (`ForgeProfileEmbedding`; branch `feature/embedded-profiles`, a prototype under evaluation for 1.0). The two share a file and a name; renaming, duplicating or deleting the Build Profile carries the Build Forge settings, and `ForgeProfile.BuildProfile` is the containing asset rather than a stored reference, so a duplicate's copy belongs to the duplicate. The package ships no conversion from the earlier layout, a separate `ForgeProfile` asset referencing its Build Profile: nothing had been released, and the projects that used it were converted with one-off scripts. Only a profile made in code (tests) still resolves its Build Profile through the stored `buildProfile` reference. The settings are edited in a "Build Forge" section after Unity's own sections in the Build Profile editor, both in the Build Profiles window and for a Build Profile asset in the Inspector; it offers adding when the profile has none and ends with a remove button. Assets > Build Forge > Add/Edit/Remove Build Forge Settings (several Build Profiles at once), the Build Profile inspector's context menu and the build window's Open in Inspector (which selects the stored component, shown by the Build Forge profile inspector) are the other entry points. An earlier header row drawn through `Editor.finishedDefaultHeaderGUI` was dropped once the section existed in both places: it only appeared in the Inspector and duplicated the section. Unity accepts no settings sections from packages outside the Unity registry, and the Build Profiles window draws no inspector header, so `BuildProfileEditorSection` inserts a foldout before the editor's "Add Settings" button (`bp-add-settings-button`, present in both), reads the profile from the window's `buildProfileEditor` field or from the Inspector's `InspectorElement.editor`, and draws the profile inspector there without the Build Profile field and the Player Overrides diff, which that editor already shows. These names are internal (the same on 6000.3.0f1 and 6000.6.3f1); where one is missing, no section is added. Earlier analysis read the missing extension point as "Build Forge cannot add UI there"; inserting into the UI Toolkit tree is unsupported but works, and fails safe. Only Build Profile assets under `Assets/` can hold the settings; Unity's platform profiles live in `Library/`.

Tested empirically on 6000.3.0f1, 6000.6.0f1 and 6000.6.3f1 (October 2026) with a stand-in type from a `file:` package (plain fields, an asset reference, a `[SerializeReference]` list): the API is `T CreateComponent<T>()` / `void AddComponent<T>(T)` / `GetComponent<T>()` / `RemoveComponent<T>()` with no registry gate; the component survived defines and development-flag changes, activation, `SerializePlayerSettings`, `ForceReserializeAssets`, player builds and, on a Build Profile with its own Player, Quality and Graphics Settings, Unity's writes of those, with its YAML block byte-identical throughout; the Build Profiles window's Duplicate (`BuildProfileDataSource.DuplicateAsset(profile, isClassic: false)`) and `AssetDatabase.CopyAsset` copy it as a distinct object; with the package removed the Build Profile still loads, saves and builds, the orphaned block is kept, nothing is logged, and re-adding the package restores the data. The component is a YAML document of its own in the profile file, so a one-field change is a one-line diff. Not covered: how the Build Profiles window and its inspector present a third-party component.

The reasons the separate asset was kept until then, verified against UnityCsReference (branches 6000.3 and 6000.4, August 2026), and what remains of them:

1. **The "Add Settings" UI is closed to us.** In 6.3 the dropdown is a hard-coded internal list (`AddSettingsDataProvider.s_InternalSettings`). In 6.4, `PackageSettingsProvider.Get()` discovers `[BuildProfileSettingsProvider]` methods but rejects any package whose `PackageInfo.GetAvailableRegistryType()` is not `RegistryType.UnityRegistry` ("Unsupported package registry type"). The attribute's own doc comment says "Currently only implementations from specific Unity packages are supported." A `file:`/git/scoped-registry package cannot appear in the dropdown, and the Build Profiles window does not render components added through the API from unregistered types. Embedding would therefore give no native UI — Build Forge would still draw everything itself.

2. **One instance per type forces 1:1.** Build Forge now enforces 1:1 itself (see "One Build Forge Profile per Unity Build Profile" under Design Principles), so this is no longer a difference between the two models.

3. **The remaining benefits are moderate.** Lifecycle coupling (no dangling references, duplication carries the config) and a one-line `GetActiveComponent<T>()` lookup, against: editing would live only in the Build Forge window (Unity's Build Profile inspector cannot be extended, and overriding it is not an option), our data would sit in Unity's profile file next to the Player Settings override blob (still readable YAML, but mixed diffs), and 20 editor files assume a standalone asset. The migration objection lapsed pre-release.

What tipped the balance: the 1:1 rule removed the strongest objection, a Build Forge Profile next to its Build Profile could not share its name in the same folder, and choosing the separate asset for 1.0 would have made a later move to a component (needed for a native foldout) a breaking migration. **Revisit** the editing location when Unity lifts the registry gate in `PackageSettingsProvider` (the check is a single line and the docs say "currently"): `[BuildProfileSettingsProvider]` would then give the stored component a native foldout in the Build Profiles window.

### Bundled Plugins as Third-Party Assemblies (not yet done)
The four plugins in the core assembly (Build Number, Git Metadata, Cloud Diagnostics, Android Keystore Env) depend on the public API plus two internals: `GitHelper` and one use of `ForgePluginRegistry`; OpenXR additionally uses `SerializedPropertySnapshot` through `InternalsVisibleTo`. When the plugin authoring guide is written (RELEASE-STATUS, after a real project has been converted), move the bundled plugins into their own assemblies *without* `InternalsVisibleTo`, so they compile exactly as a third party's would. That is the proof that the public API suffices, and it forces the deferred decisions: whether `GitHelper` becomes a public authoring utility, and whether first-party-only access to `SerializedPropertySnapshot` stays a privilege of the OpenXR plugin. `PublicApiSurfaceTests` locks whatever gets promoted. Not done now because splitting with `InternalsVisibleTo` proves nothing and only costs compile time, and splitting without it is API design that should follow the conversion experience.

### Build Parameters (not yet implemented)
Build variants are one instance of a general thing: a per-build choice, picked in the window or on the command line, that changes what a build does. Two thirds of the variant feature could have been a plugin (`OnPreBuild`/`OnPostBuild` for the define and the marked product name, `IForgeEditorApplicable` for editor iteration, `OnDrawSettingsGUI` for the list, `IForgeManifestContributor` for the manifest, `DescribeBuild` for the window); the third that could not is the choice itself, because a new independent choice would need its own selector and CLI argument. The existing variant choice is available to plugins through the build context and variant-aware validation, description and editor Apply hooks. The generalization is "build parameters": a plugin declares a parameter (name, allowed values), the core collects the choice in the action bar and as a CLI argument, resolves it strictly, exposes it in `ForgeBuildContext`, offers it as an output-path placeholder and records it in the manifest; plugins implement the behavior. Variants would then be a bundled plugin declaring one parameter, keeping `-forgeVariant`, `{Variant}` and `BuildVariant` as that parameter's conventions so nothing changes for users. Not worth the abstraction for one choice; do it when a second per-build choice appears (a distribution channel, a region), and move variants onto it then.

### Profile Inheritance (not yet implemented)
Would allow a ForgeProfile to have a parent ForgeProfile, inheriting plugin configs. Useful for Dev/Staging/Release variations. The main design question: how does inheritance interact with per-plugin config objects? Likely needs a merge strategy per plugin.

### Apply Profile to Editor — implemented; coverage lint still open
The apply-from-baseline mechanism and optional XR loader plugin are implemented
(see "Editor State" under Core Architecture and Development~/VARIANTS-AND-XR.md). The
loader plugin uses the same baseline machinery. The remaining design item is:
- **Coverage validation (the lint).** Per plugin, per shared scope (all profiles whose Build Profile shares a `BuildTargetGroup`): any setting overridden by *any* profile should be specified by *every* profile, otherwise it silently inherits the baseline. Fits the existing `Validate(ForgeProfile)` hook as a build-window warning ("'SteamFrame' leaves `symmetricProjection` at No Override, but 'Quest' overrides it"). With the baseline invariant in place this is a lint for intent, not a safety mechanism — holes resolve to the baseline, never to the previously applied profile.

Design change from the original brief: the baseline is captured fresh at every apply (right after the previous profile is reverted) and exists only while a profile is applied, rather than being a permanent declared snapshot with a manual "Reset Baseline". A permanent baseline goes stale the moment someone reverts, hand-edits, and re-applies; the while-applied model cannot.

### Out-of-Process Build Orchestrator (not yet implemented)
A lightweight local CI that runs builds in separate Unity processes. Would enable cross-platform builds without asset reimport delays, atomic version bumping, parallel builds, and batch sequences of profiles. Build Forge itself runs one profile at a time — multi-profile workflows belong here, since they need to handle package changes between builds (domain reloads destroy in-process build state).

### Per-Profile Package Management (not yet implemented)
Unity's `Packages/manifest.json` is global — there's no built-in way to have different packages per Build Profile.

**Intended approach**: Store a full `manifest.json` snapshot per ForgeProfile. Switching the active profile in the editor writes that profile's manifest, triggering a domain reload. When the user modifies packages, the updated manifest is saved back to the profile. Single-profile-at-a-time by design — building multiple profiles with different packages requires the out-of-process orchestrator.

**Open problem**: `manifest.json` is in version control. If two developers work on different profiles, they commit different `manifest.json` states and conflict. Options: `.gitignore` manifest and reconstruct from active profile, or accept last-commit-wins with Build Forge overwriting on profile switch. Neither is fully satisfying.

**Workaround available today**: For cases where you want to exclude code (not native plugins or shader variants) from specific profiles, use `defineConstraints` on assembly definitions gated by per-profile scripting defines. Code in assemblies with unsatisfied constraints doesn't compile — functionally equivalent to removing the package for code-only dependencies. This is the same pattern Build Forge uses internally for its OpenXR and Addressables plugin assemblies. For an XR vendor SDK's Android libraries and manifest entries, the XR Vendor Filter excludes them per profile (see "XR Vendor SDKs in Other Vendors' Builds").
